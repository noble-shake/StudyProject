## 정의

PHP는 웹 서버에서 HTML이나 JSON 같은 응답을 만들어내기 위해 만들어진 서버 사이드 스크립트 언어다.
"서버 사이드"라는 말이 핵심인데, PHP 코드는 사용자의 브라우저가 아니라 웹 서버(우리 경우엔 Apache)
위에서 실행되고, 그 실행 결과(완성된 HTML이나 JSON 텍스트)만 브라우저로 전송된다. 자바스크립트가
브라우저 안에서 실행되는 것과 정반대 위치에 있는 언어라고 생각하면 된다.

PHP의 가장 큰 특징은 "요청마다 새로 실행된다"는 점이다. 사용자가 `get_posts.php`에 접속하면, 서버는
그 요청 하나를 위해 `get_posts.php` 파일을 처음부터 끝까지 다시 실행하고, 끝나면 메모리에서 사라진다.
Node.js처럼 서버 프로세스가 계속 떠 있으면서 요청을 하나씩 처리하는 방식과는 실행 모델 자체가 다르다.

## 요약

PHP는 "요청 하나 = 스크립트 한 번 실행"이라는 모델을 가진 서버 사이드 언어이고, 이 프로젝트는
그 위에 아무 프레임워크도 얹지 않은 채로 직접 썼다 — 그 결과 "파일 경로가 곧 URL 경로"가 되는
가장 원초적인 형태의 라우팅을 갖게 됐다.

## 상세

### 왜 이런 실행 모델을 갖게 됐나

PHP는 1990년대 중반, "홈페이지에 방문자 수 세는 스크립트를 붙이고 싶다"는 아주 실용적인 동기에서
출발했다. 그래서 처음부터 "이 파일 하나가 하나의 요청을 처리한다"는 단순한 모델을 택했고, Apache 같은
웹 서버에 모듈로 꽂히면서 "URL 경로 = 서버의 실제 파일 경로"라는 관례가 자연스럽게 생겼다. 이 관례가
지금 RottenNobleProject의 백엔드 구조를 그대로 설명한다.

### 프레임워크 없이 쓴다는 것의 실제 의미

Laravel이나 Symfony 같은 PHP 프레임워크를 쓰면, 라우터가 URL을 분석해서 어떤 컨트롤러 함수를
호출할지 정해주고, ORM이 DB 접근을 대신해주고, 미들웨어 체인이 인증 같은 공통 처리를 앞뒤로
끼워준다. RottenNobleProject는 이런 걸 하나도 쓰지 않았다. 그 대신:

- **라우팅**: `backend/get_posts.php`라는 파일이 있으면 `/get_posts.php`가 곧 그 엔드포인트다.
  라우터가 URL을 해석하는 과정 자체가 없다 — 웹 서버(Apache)가 그냥 그 경로의 파일을 실행할 뿐이다.
- **컨트롤러**: 각 `.php` 파일 자체가 컨트롤러 역할을 한다. `get_posts.php`를 열어보면
  `require`로 공통 유틸을 불러오고, SQL을 실행하고, JSON으로 응답하는 게 전부다 — 딱 20줄
  안팎이다.
- **미들웨어**: `auth.php`의 `require_admin()` 함수를 보호가 필요한 엔드포인트 맨 위에서 그냥
  호출한다. Express나 Laravel의 미들웨어 체인처럼 "요청이 여러 겹의 함수를 자동으로 통과하는"
  구조가 아니라, 개발자가 매 파일마다 "여기서 로그인 확인해줘"라고 직접 한 줄을 적어 넣는 방식이다.
  빼먹으면 그 엔드포인트는 그냥 보호가 안 된다 — 프레임워크였다면 라우트 정의에서 강제할 수 있었을
  실수를, 여기서는 개발자의 습관에 맡기고 있다는 뜻이다.

### 반복을 뽑아내는 방식

프레임워크가 없다 보니, 여러 엔드포인트 파일에서 매번 반복되는 코드가 생긴다. 이 프로젝트에서는
CORS 헤더를 붙이고 JSON으로 응답하는 코드가 세 번째 파일에서도 똑같이 나타나자, 그걸
`response.php`라는 공용 파일로 뽑아냈다. 이건 프레임워크가 "미리 정해준" 구조가 아니라, 코드를
짜다가 중복을 발견하고 그때그때 손으로 리팩터링한 결과다.

```php
// backend/response.php — 실제 코드
function send_json($data, int $httpCode = 200): void
{
    header('Content-Type: application/json; charset=UTF-8');
    http_response_code($httpCode);
    echo json_encode(['status' => 'ok', 'data' => $data]);
    exit;
}
```

이런 식으로 "필요할 때 뽑아내는" 접근은 프레임워크가 처음부터 강제하는 구조보다 자유롭지만, 그만큼
"언제 뽑아낼지"를 사람이 계속 판단해야 한다는 대가가 있다.

## 비교표

| 항목 | PHP (프레임워크 없음, 이 프로젝트) | PHP + 프레임워크 (Laravel 등) | Node.js/Express |
|---|---|---|---|
| 실행 모델 | 요청마다 스크립트 새로 실행 | 요청마다 스크립트 새로 실행(프레임워크 부트스트랩 포함) | 프로세스가 계속 떠서 요청을 순차 처리 |
| 라우팅 | 파일 경로 = URL 경로 | 라우트 정의 파일에서 URL→컨트롤러 매핑 | 코드로 명시적 라우트 등록 |
| 공통 처리(인증 등) | 파일마다 함수 호출로 직접 삽입 | 미들웨어 체인이 자동 적용 | 미들웨어 체인이 자동 적용 |
| 학습 난이도 | 낮음(개념이 거의 없음) — 대신 "프레임워크가 원래 해주던 일"을 직접 알아야 함 | 프레임워크 고유 개념(ORM, 서비스 컨테이너 등)을 따로 배워야 함 | 이벤트 루프, 비동기 개념을 배워야 함 |
| 이 프로젝트가 고른 이유 | 엔드포인트가 10여 개뿐인 규모 + "PHP 자체를 직접 익힌다"는 학습 목표 | (선택 안 함) | (선택 안 함, 백엔드는 PHP로 고정) |

## 질문

- **Q. 왜 `require_admin()`을 매 파일마다 호출해야 하나? 자동으로 걸 수는 없나?**
  A. 프레임워크의 미들웨어 체인이 없으니 "요청이 들어오면 항상 거치는 공통 관문"이 없다. Apache
  설정(`.htaccess`)에서 특정 경로 패턴에 대해 인증을 강제하는 것도 이론적으로는 가능하지만, 이
  프로젝트는 그렇게까지 하지 않고 각 파일에 `require_admin();` 한 줄을 직접 넣는 쪽을 택했다 —
  엔드포인트가 몇 개 안 되니 실수로 빼먹을 위험보다 구조를 단순하게 유지하는 쪽을 우선한 것으로
  보인다.

- **Q. 파일 하나 = 엔드포인트 하나 구조는 엔드포인트가 많아지면 안 무너지나?**
  A. 무너진다. 지금은 10여 개라 폴더 하나에 다 펼쳐놔도 훑어보는 데 문제가 없지만, 엔드포인트가
  수십 개로 늘어나면 파일 이름만으로 구조를 파악하기 어려워지고, `response.php`처럼 뽑아낼 공통
  로직도 더 많아진다 — 이 지점이 보통 "이제 프레임워크나 최소한의 라우터가 필요하다"는 신호가 되는
  경계선이다.

## 예시 코드

실제 `backend/get_posts.php` 전체 — 프레임워크 없는 PHP 엔드포인트가 얼마나 짧을 수 있는지 보여준다.

```php
<?php
// backend/get_posts.php
require 'response.php';
require 'db.php';

allow_cors();

$sql = "SELECT id, title, content, created_at FROM posts ORDER BY created_at DESC";
$result = $conn->query($sql);

$posts = [];
if ($result->num_rows > 0) {
    while ($row = $result->fetch_assoc()) {
        $posts[] = $row;
    }
}

$conn->close();
send_json($posts);
```

`require`로 공용 유틸 두 개를 불러온 다음, CORS를 허용하고, SQL을 돌리고, JSON으로 응답한다 — 이
네 줄짜리 흐름이 이 프로젝트의 거의 모든 GET 엔드포인트에서 반복되는 뼈대다.

## 실무

실무에서는 신규 프로젝트에 프레임워크 없는 PHP를 쓰는 경우가 많지 않다 — Laravel이 사실상 PHP
생태계의 표준 프레임워크로 자리잡았고, 라우팅·ORM·인증·검증 같은 걸 직접 짜는 대신 프레임워크가
제공하는 규약을 따르는 쪽이 유지보수 비용이 훨씬 낮기 때문이다. 다만 이 프로젝트처럼 규모가 아주
작고(엔드포인트 10여 개), 목적 자체가 "PHP 언어와 웹 서버가 어떻게 맞물려 동작하는지 직접 익히는
것"이라면, 프레임워크가 대신 해주는 부분을 일부러 걷어내고 직접 짜보는 것도 합리적인 선택이다.
프레임워크는 "이미 이해한 것을 빠르게 반복하기 위한 도구"에 가깝다 — 처음 배우는 단계에서는 오히려
무엇이 자동으로 되는지가 안 보여서 방해가 될 수 있다.

최근 동향으로는 PHP 자체도 8.x 버전대에서 타입 선언, `match` 표현식, 성능 개선(JIT 컴파일러)이
계속 들어가고 있고, "레거시 언어"라는 이미지와 달리 워드프레스 등 대규모 서비스가 여전히 PHP
위에서 돌아가고 있다.
