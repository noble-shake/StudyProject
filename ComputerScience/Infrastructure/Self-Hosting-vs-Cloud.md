## 정의

웹 서비스를 인터넷에 띄우는 방법은 크게 두 갈래다. **클라우드**(AWS, GCP, Azure 등)는 다른
회사가 소유·관리하는 서버 자원을 필요한 만큼 빌려 쓰는 방식이고, **자체 호스팅(self-hosting)**은
개인이나 조직이 직접 소유한 하드웨어(이 프로젝트의 경우 가정용 NAS)를 서버로 운영하는 방식이다.

## 요약

RottenNobleProject가 Synology NAS를 프로덕션 서버로 고른 이유는 "기술적으로 더 낫다"가 아니라
"이미 개인적으로 갖고 있는 하드웨어가 있으니 계속 돈이 드는 클라우드를 쓸 이유가 없다"는 아주
실용적인 판단이었다 — 대신 그 대가로 클라우드였다면 안 겪었을 인프라 함정들을 여러 번 직접
마주쳤다.

## 상세

### 왜 NAS를 골랐나

`04_CURRENT_PROJECT.md`에 남아있는 이유는 명확하다: "AWS 등 클라우드는 계속 비용이 드는데,
이미 개인용으로 갖고 있는 NAS가 있어서 그걸 활용 — 돈을 내면서 클라우드 쓸 이유가 없다는 판단."
이건 순수하게 비용 관점의 결정이고, 동시에 이 프로젝트의 또 다른 목표인 "직접 인프라를 만져보는
경험" 자체가 학습 목표 중 하나라는 점과도 맞아떨어진다 — 클라우드의 관리형 서비스는 이런 종류의
인프라 디테일을 대부분 가려주기 때문에, 오히려 "덜 편한" NAS 쪽이 배울 게 더 많다.

### 이 선택이 실제로 만들어낸 제약들

일단 NAS로 정해지자, 그 뒤의 여러 기술 선택이 거기서 역산됐다:

- **DB가 MariaDB인 이유** — Synology 패키지 센터가 기본 지원하는 관계형 DB가 MariaDB라서
  ([MariaDB](../Database/MariaDB.md) 참고). 클라우드였다면 RDS에서 MySQL/PostgreSQL/MariaDB 중 자유롭게
  골랐을 것이다.
- **로컬 개발 환경이 XAMPP인 이유** — 프로덕션이 Apache 기반 Web Station이라, 로컬도 같은
  Apache+PHP 조합으로 맞춰서 "로컬에서 되면 배포해서도 될 확률"을 높이려는 판단.
- **포트/인증서 함정들** — 클라우드 로드밸런서나 관리형 인증서 서비스(AWS Certificate Manager
  등)를 쓴다면 자동으로 처리됐을 일들(포트 충돌, ACME 챌린지 라우팅)을 전부 직접 겪었다
  ([HTTPS & Mixed Content](../Network/HTTPS-and-Mixed-Content.md) 참고).

### 클라우드였다면 안 겪었을 것, 그래도 얻은 것

이 프로젝트가 실제로 겪은 함정들(`MEMO-WEB-06`에 기록된 7개 항목 — 경로 인식 실패, PHP 프로파일
미등록, 포트 충돌, 인증서 발급 실패 등)은 대부분 "관리형 클라우드 서비스였다면 애초에 신경 쓸
필요가 없었을" 종류의 문제다. AWS Elastic Beanstalk나 관리형 RDS를 썼다면, 포트 충돌이나 PHP
런타임 등록 같은 걸 사용자가 직접 만질 일이 거의 없다.

반대로, 바로 그 "직접 만져야 했다"는 점이 이 프로젝트의 학습 목표(인프라 경험) 관점에서는
얻은 것이기도 하다 — 포트포워딩이 무엇이고 왜 필요한지, ACME 챌린지가 실제로 어떻게 동작하는지,
가상 호스트가 무엇인지를 추상화된 클라우드 콘솔 뒤에 숨지 않고 직접 부딪혀보며 배웠다.

## 비교표

| 항목 | Synology NAS 자체 호스팅 (이 프로젝트) | 클라우드(AWS 등) |
|---|---|---|
| 비용 구조 | 하드웨어를 이미 보유 — 추가 비용 거의 없음(전기세 제외) | 사용량에 비례한 지속적 과금 |
| 초기 설정 난이도 | 높음(포트·가상 호스트·인증서를 직접 설정) | 낮음(관리형 서비스가 대부분 처리) |
| 장애 시 복구 | 직접 진단·복구(NAS가 죽으면 서비스 전체 중단) | 관리형 서비스의 이중화/자동 복구 옵션 |
| 확장성(트래픽 급증 대응) | 하드웨어 성능에 물리적으로 제한됨 | 필요에 따라 자동/수동 확장 가능 |
| 인프라 학습 효과 | 큼(포트·인증서·가상 호스트를 직접 다룸) | 작음(대부분 추상화되어 안 보임) |
| 이 프로젝트가 고른 이유 | 비용 + 인프라 직접 경험이라는 학습 목표 | (선택 안 함) |

## 질문

- **Q. 트래픽이 갑자기 늘어나면 NAS로 버틸 수 있나?**
  A. 개인 포트폴리오 블로그 규모(방문자가 아주 많지 않음)에서는 문제가 없지만, 만약 어떤 계기로
  트래픽이 크게 늘어난다면 가정용 인터넷 회선의 업로드 대역폭과 NAS의 처리 성능이 물리적인
  한계가 된다. 클라우드였다면 이런 상황에서 서버를 더 붙이거나 사양을 올리는 게 몇 분 안에
  가능하지만, NAS는 하드웨어를 바꾸지 않는 한 그 한계를 넘을 수 없다.

- **Q. NAS가 고장 나거나 정전이 나면 어떻게 되나?**
  A. 서비스가 그대로 중단된다. 클라우드의 여러 가용 영역(availability zone)에 걸친 이중화 같은
  장치가 이 구성엔 없다 — 이것도 "개인 프로젝트라 감수 가능한" 리스크와, "실제 상업 서비스라면
  받아들이기 어려운" 리스크의 경계를 보여주는 지점이다.

## 실무

실무에서는 개인 프로젝트나 아주 작은 팀이 비용 절감을 위해 자체 호스팅(홈서버, 소형 VPS 등)을
쓰는 경우가 있지만, 상업 서비스나 회사 프로덕션 환경에서는 거의 항상 클라우드 또는 전문
데이터센터 코로케이션을 쓴다 — 가용성(uptime) 보장, 보안 패치, 물리적 장애 대응 같은 걸 개인이
감당하기 어렵기 때문이다. 다만 "자체 호스팅으로 인프라를 직접 배워본다"는 경험 자체는 실무에서도
가치를 인정받는다 — 클라우드의 관리형 서비스가 왜 그렇게 설계됐는지(로드밸런서, 인증서 자동
갱신, 오토스케일링 등)를 그 문제를 직접 겪어본 사람이 훨씬 잘 이해하기 때문이다. 최근 동향으로는
"홈랩(homelab)" 문화가 개발자 커뮤니티에서 여전히 활발하고, 이 프로젝트도 정확히 그 계열에
속한다.
