## 출처

`RottenNobleProject` — `RottenNobleProject-Architecture.md` 3회차(인증 흐름) 코드 학습에서
`login.php`의 `password_verify()` 호출을 보다가 분리한 주제.

## 정의

비밀번호 해싱은 사용자의 실제 비밀번호를 데이터베이스나 설정 파일에 그대로 저장하지 않고, **되돌릴
수 없는 변환(해시 함수)**을 거친 값만 저장하는 방법이다. 로그인 시에는 사용자가 입력한 비밀번호를
같은 방식으로 변환해서 저장된 해시와 비교한다 — 원래 비밀번호가 무엇이었는지는 그 해시값만 봐서는
알아낼 수 없다.

## 요약

이 프로젝트는 관리자 비밀번호를 평문이 아니라 bcrypt 해시로 저장하고, `password_verify()`로
검증한다 — 관리자가 한 명뿐인 아주 작은 시스템이지만, 이 부분만큼은 실무 표준을 그대로 따른
지점이다.

## 상세

### 왜 평문 저장이 안 되나

만약 비밀번호를 그대로 저장한다면, 설정 파일이나 DB가 유출되는 순간 모든 사용자의 실제 비밀번호가
그대로 노출된다. 이 프로젝트가 실제로 겪은 `MEMO-WEB-01`(DB 접속 정보가 평문으로 git에 커밋된 적
있음)과 같은 종류의 사고가 비밀번호에서 일어난다고 생각하면, 왜 이게 중요한지 바로 와닿는다.
해싱은 "유출되더라도 원래 비밀번호를 바로 알아낼 수는 없게" 만드는 마지막 방어선이다.

### 왜 단순 해시(SHA-256 등)로는 부족한가

"되돌릴 수 없는 변환"이라면 SHA-256 같은 일반 해시 함수를 써도 되지 않을까 싶을 수 있다. 문제는
속도다. SHA-256은 원래 "빠르게" 계산되도록 설계됐다 — 파일 무결성 검증 같은 용도에는 그게
장점이지만, 비밀번호에는 정반대로 작용한다. 공격자가 유출된 해시값을 놓고 "이 문자열들을 SHA-256에
넣어보면서 같은 해시가 나오는 걸 찾는" **무차별 대입(brute-force)** 공격을 할 때, 해시 계산이
빠를수록 공격자가 초당 시도할 수 있는 횟수가 늘어난다. 최신 GPU는 SHA-256을 초당 수십억 번씩
계산할 수 있다.

bcrypt는 의도적으로 계산이 느리도록 설계됐다(그리고 그 느린 정도를 "cost factor"로 조절할 수
있다). 정당한 로그인 시도 한 번에 몇 십~몇 백 밀리초가 걸리는 건 사용자 입장에서 체감이 안
되지만, 공격자가 수십억 개의 후보를 시도해야 하는 무차별 대입 공격에서는 이 속도 차이가 공격
시간을 현실적으로 불가능한 수준까지 늘려버린다.

### `salt`가 자동으로 처리된다는 것

같은 비밀번호를 쓰는 두 사용자가 있다면, 단순 해시는 정확히 같은 해시값을 만들어낸다 — 이러면
공격자가 "흔한 비밀번호의 해시값을 미리 계산해둔 표"(레인보우 테이블)로 여러 계정을 한꺼번에
공격할 수 있다. bcrypt는 해시를 계산할 때마다 무작위 "salt"(양념) 값을 섞어서, 같은 비밀번호라도
매번 다른 해시값이 나오게 만든다. PHP의 `password_hash()`는 이 salt를 자동으로 생성해서 해시값
안에 함께 저장해준다 — 개발자가 salt를 따로 관리할 필요가 없다.

```php
// config.example.php의 주석이 이미 알려주는 규칙
// password_hash('실제비밀번호', PASSWORD_BCRYPT)의 결과만 넣는다 — 평문 금지.
'admin_password_hash' => '',
```

```php
// login.php — 실제 검증 코드
$validPass = $password !== '' && password_verify($password, $config['admin_password_hash'] ?? '');
```

`password_verify($password, $hash)`는 내부적으로 `$hash`에 저장된 salt를 다시 꺼내 같은 방식으로
계산한 뒤 비교해준다 — 개발자는 salt를 신경 쓸 필요 없이 이 함수 하나만 쓰면 된다.

## 비교표

| 방식 | 되돌릴 수 없나 | 계산 속도(의도적으로) | Salt 자동 처리 | 이 프로젝트 사용 여부 |
|---|---|---|---|---|
| 평문 저장 | 아니오(그대로 노출) | - | - | 사용 안 함 |
| SHA-256 등 일반 해시 | 예 | 빠름(공격에 유리) | 직접 구현 필요 | 사용 안 함 |
| bcrypt (`password_hash`) | 예 | 느림(공격에 불리, 조절 가능) | 자동 | **사용 중** |
| Argon2 (`PASSWORD_ARGON2ID`) | 예 | 느림, 메모리도 많이 씀(더 강함) | 자동 | 사용 안 함(bcrypt로 충분한 규모) |

## 질문

- **Q. bcrypt 대신 Argon2를 쓰는 게 더 낫지 않나?**
  A. Argon2(특히 Argon2id)가 현재 시점에서는 더 최신이고, 메모리를 많이 요구하도록 설계돼 GPU
  기반 공격에 더 강하다는 평가를 받는다. 다만 bcrypt도 여전히 널리 쓰이고 검증된 방식이라, 관리자
  한 명만 로그인하는 이 프로젝트 규모에서는 실질적인 차이가 크지 않다. PHP는 `password_hash()`
  함수 하나로 두 방식을 알고리즘 상수만 바꿔서 전환할 수 있어(`PASSWORD_BCRYPT` ↔
  `PASSWORD_ARGON2ID`), 나중에 필요해지면 전환 비용이 크지 않다.

- **Q. 관리자가 한 명뿐인데 이렇게까지 신경 쓸 필요가 있었나?**
  A. 있다. 사용자 수와 별개로, 해싱을 제대로 안 하면 "DB나 설정 파일이 유출됐을 때의 피해 규모"가
  완전히 달라진다. 사용자가 한 명이어도 그 한 명의 비밀번호가 평문으로 노출되는 것과, bcrypt
  해시만 노출되는 것은 실질적 피해 차원이 다르다 — 이건 규모와 무관하게 항상 지켜야 하는 최소
  기준에 가깝다.

## 예시 코드

```php
// 비밀번호를 처음 설정할 때 (관리자가 직접 한 번 실행해서 해시를 만들고, 그 결과를
// config.local.php에 붙여넣는 방식 — 이 프로젝트엔 별도 "회원가입" 플로우가 없다)
echo password_hash('실제비밀번호', PASSWORD_BCRYPT);
// 출력 예: $2y$10$N9qo8uLOickgx2ZMRZoMy... (이 문자열 전체를 저장한다)
```

```php
// 로그인 시 검증
if (password_verify($inputPassword, $storedHash)) {
    // 일치
}
```

## 플로우차트

(생략 — "해시를 만들 때 한 번, 검증할 때 한 번, 함수 호출로 끝난다"는 흐름이라 그림이 필요한
분기나 순서가 없다.)

## 실무

`password_hash()`/`password_verify()`는 PHP 생태계에서 비밀번호를 다룰 때 사실상 표준이다 —
직접 해싱 알고리즘을 구현하거나 오래된 `md5()`/`sha1()`을 쓰는 코드를 실무에서 새로 작성하는
경우는 이제 거의 없다(있다면 레거시 코드 리뷰에서 바로 지적될 사안이다). 최근에는 bcrypt보다
Argon2id를 기본으로 권장하는 흐름이 있지만, 두 방식 모두 여전히 실무에서 널리 쓰이는 안전한
선택지다. 중요한 실무 원칙은 "직접 암호학 알고리즘을 설계하지 않는다"는 것 — 검증된 표준
함수만 쓴다.
