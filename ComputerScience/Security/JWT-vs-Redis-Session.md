## 정의

로그인 후 "이 사용자가 계속 로그인 상태다"라는 걸 서버가 매 요청마다 어떻게 확인할지 정하는 방식이
크게 두 갈래로 나뉜다. 하나는 서버가 발급한 토큰을 **서버 쪽 저장소에 보관**해두고 매번 그 저장소를
조회해서 확인하는 방식(세션 방식, 이 프로젝트가 Redis로 구현한 것)이고, 다른 하나는 토큰 **자체에
서명을 넣어서** 저장소 조회 없이 서명만 검증하면 되게 만드는 방식(JWT, JSON Web Token)이다.

## 요약

RottenNobleProject는 Redis 기반 세션을 골랐고, 그 덕분에 "로그아웃하면 그 즉시, 확실하게 무효화"가
가능하다 — JWT였다면 이게 기본으로는 안 되는, 이 프로젝트가 실제로 얻은 것과 포기한 것이 명확히
갈리는 지점이다.

## 상세

### 세션 방식 — "토큰은 열쇠, 진짜 정보는 서버 금고에"

이 프로젝트가 실제로 구현한 방식이다. `login.php`가 로그인에 성공하면 무작위 문자열(토큰)을
만들어 클라이언트에 준 다음, "이 토큰 = 관리자"라는 사실 자체는 서버 쪽 Redis에 저장해둔다.
토큰 자체에는 아무 정보도 없다 — 그냥 무작위 문자열일 뿐이고, 그 문자열이 의미를 가지려면 매번
Redis에 물어봐야 한다. 그래서 이 방식을 "opaque(불투명) 토큰"이라고도 부른다 — 토큰만 봐서는
아무것도 알 수 없기 때문이다.

```php
// login.php — 토큰 생성과 저장이 분리돼 있다
$token = bin2hex(random_bytes(32));      // 그냥 무작위 문자열
$redis->set("admin_session:$token", 'admin', 86400); // 의미는 여기(서버)에만 있다
```

### JWT 방식 — "토큰 안에 이미 정보와 서명이 들어있다"

JWT는 정반대 철학이다. 토큰 자체가 `헤더.페이로드.서명` 세 부분으로 이루어져 있고, 페이로드
안에 "누구인지, 언제 발급됐는지, 언제 만료되는지"(`exp` 클레임) 같은 정보가 그대로 들어있다.
서버는 이 토큰을 받으면, 저장소를 조회할 필요 없이 **서명만 검증**하면 된다 — 서명이 서버만 아는
비밀 키로 만들어졌다는 것만 확인하면, 토큰 안의 내용이 위조되지 않았다고 믿을 수 있다. 그래서
"stateless(무상태)" 인증이라고 부른다 — 서버가 어떤 세션도 기억하고 있을 필요가 없기 때문이다.

### 왜 이 프로젝트는 세션(Redis)을 골랐나

`CODE_MEMO.md`의 `MEMO-WEB-04`에 남아있는 이유는 단순하다 — **즉시, 확실한 무효화**가 필요했기
때문이다. 관리자가 로그아웃하면(`logout.php`), 서버는 Redis에서 그 토큰을 `DEL`로 바로 지워버릴
수 있다. 그 순간부터 그 토큰은 완전히 죽은 토큰이다.

JWT였다면 이게 훨씬 까다롭다. 서버가 서명만 검증하고 저장소를 안 본다는 게 JWT의 핵심 장점인데,
그 말은 곧 "이미 발급된 토큰을 강제로 무효화할 방법이 기본적으로 없다"는 뜻이기도 하다. 토큰이
만료 시각(`exp`)에 도달하기 전까지는, 서버가 "이 토큰은 이제 못 쓴다"고 선언할 저장소 자체가
없다. 이걸 해결하려면 결국 "무효화된 토큰 블록리스트"를 서버 쪽에 별도로 둬야 하는데, 그 순간
JWT의 "저장소 조회가 필요 없다"는 장점이 사실상 사라진다 — 블록리스트도 결국 매 요청마다 조회해야
할 저장소이기 때문이다.

이 프로젝트는 이미 `RottenNoble-HttpServer`/`TCPServer`와 Redis 인프라를 공유하고 있었다는 점도
컸다 — 세션 저장소로 쓸 Redis가 어차피 이미 있었으니, JWT가 주는 "저장소가 필요 없다"는 이점
자체가 이 프로젝트에는 크게 매력적이지 않았다.

### 실제 위험: 토큰이 새어나갔을 때

두 방식의 차이가 가장 극명하게 드러나는 시나리오는 "토큰이 유출됐다는 걸 방금 알았다"는 상황이다.

- **Redis 세션(이 프로젝트)**: 관리자가 `logout.php`를 호출하거나, 서버 운영자가 Redis에서 직접
  그 키를 지우면 그 즉시 끝난다. 유출된 토큰은 다음 요청부터 바로 401을 받는다.
- **JWT**: 만료 시각까지는 막을 방법이 없다(블록리스트를 미리 만들어두지 않았다면). 그래서 JWT를
  쓰는 실무 시스템들은 대개 만료 시간을 짧게(예: 15분) 잡고, 그 대신 "리프레시 토큰"이라는 별도
  토큰으로 짧은 토큰을 계속 재발급받는 2단계 구조를 쓴다 — 결국 리프레시 토큰 쪽은 서버가 상태를
  들고 있어야 해서, 완전히 무상태인 JWT는 실무에서 드물다.

## 비교표

| 항목 | Redis 세션 (이 프로젝트) | JWT |
|---|---|---|
| 토큰 자체에 정보가 있는가 | 없음(무작위 문자열) | 있음(페이로드가 그대로 담김) |
| 검증 방법 | 매 요청마다 서버 저장소(Redis) 조회 | 서명 검증만(저장소 조회 불필요) |
| 여러 서버에 걸친 검증 | 저장소를 공유하면 가능(이 프로젝트가 이렇게 함) | 비밀 키만 공유하면 저장소 없이 가능 |
| 즉시 무효화(로그아웃) | 기본 기능(`DEL` 한 번) | 기본으로는 불가능 — 블록리스트 별도 구현 필요 |
| 서버 확장성(수평 확장) | 세션 저장소가 병목이 될 수 있음 | 저장소 조회가 없어 이론상 더 유리 |
| 이 프로젝트가 실제로 얻은 것 | 즉시·확실한 로그아웃 | (선택 안 함) |
| 이 프로젝트가 포기한 것 | (해당 없음, 애초에 확장성이 중요하지 않은 규모) | (선택 안 함이므로 해당 없음) |

## 질문

- **Q. 이 프로젝트 규모(관리자 1명)에서 확장성 차이가 실제로 의미가 있었을까?**
  A. 거의 없다. JWT가 유리해지는 시나리오는 "인증 서버와 별개로 여러 API 서버가 각자 독립적으로
  토큰을 검증해야 하고, 그 서버 수가 늘어날 때"인데, 이 프로젝트는 관리자 한 명이 쓰는 개인
  블로그라 애초에 그런 확장이 일어날 일이 없다. 그래서 이 선택은 "확장성보다 즉시 무효화를
  우선했다"기보다, "확장성이 애초에 이 프로젝트에서 고려 대상이 아니었다"에 더 가깝다.

- **Q. 그럼 언제 JWT를 고르는 게 맞나?**
  A. 여러 독립된 서비스(마이크로서비스)가 같은 사용자를 인증해야 하는데, 그 서비스들이 매번
  하나의 중앙 세션 저장소에 물어보는 게 병목이 되는 상황. 혹은 인증 서버와 리소스 서버가 물리적으로
  분리돼 있어 세션 저장소를 공유하기 어려운 상황. 이런 경우엔 "일단 서명만 검증하고, 정말
  민감한 작업 전에만 추가 확인" 같은 절충이 JWT의 이점을 살릴 수 있다.

- **Q. "Redis 세션도 결국 저장소 조회가 필요하니 JWT의 무상태성만큼 빠르지 않다"는 말이 맞나?**
  A. 맞다. 다만 Redis 자체가 메모리 기반이라 그 조회 자체가 매우 빠르다([Redis](../Infrastructure/Redis.md) 참고).
  "저장소 조회가 없다"는 JWT의 이론적 이점이 실무에서 체감될 만큼 크려면, 그 저장소 조회가 실제
  병목이 될 정도의 트래픽 규모여야 한다 — 이 프로젝트는 그런 규모가 전혀 아니다.

## 예시 코드

```php
// 이 프로젝트: Redis 세션 검증 (backend/auth.php)
$value = $redis->get("admin_session:$token");
if ($value !== 'admin') {
    send_error('세션이 유효하지 않거나 만료되었습니다.', 401);
}
```

```text
// 참고: JWT였다면 이 검증이 이런 모양이 됐을 것이다 (이 프로젝트엔 없는 코드, 개념 설명용)
$payload = JWT::decode($token, $secretKey, ['HS256']);
if ($payload->exp < time()) {
    send_error('토큰이 만료되었습니다.', 401);
}
// Redis 조회가 아예 없다 — 대신 로그아웃을 강제할 방법도 여기 없다
```

## 실무

실무에서는 두 방식 다 널리 쓰이고, "무조건 이게 낫다"는 정답은 없다 — 시스템의 형태에 따라 갈린다.
단일 서버나 소수의 서버가 하나의 세션 저장소(Redis 등)를 공유할 수 있는 구조라면 세션 방식이
여전히 흔하고, 특히 이 프로젝트처럼 "즉시 로그아웃"이 중요한 서비스(뱅킹, 관리자 페이지)에서
선호된다. 반대로 OAuth2/OIDC 기반의 대규모 마이크로서비스, 여러 회사의 서비스가 서로의 인증을
믿어야 하는 연합 인증(federated auth) 상황에서는 JWT(또는 그 사촌 격인 OAuth Access
Token)가 사실상 표준이다. 최근 동향으로는 "JWT를 쓰되 만료 시간을 짧게 잡고, 그 대신 서버 쪽에
상태를 갖는 리프레시 토큰을 따로 둔다"는 하이브리드 구조가 실무에서 가장 흔한 절충안이다 — 순수
무상태 JWT만 쓰는 경우는 생각보다 드물다.
