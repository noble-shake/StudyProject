## 출처

2026-09-08, 사이트가 스캔/프로빙을 당한 뒤 "DB가 통째로 유출되면 방명록에 남긴 이름까지 그대로
읽힌다"는 지점이 눈에 띄어, 방명록 `name` 컬럼에 암호화를 붙이면서 정리한 주제.
[Password-Hashing](./Password-Hashing.md)과 자주 헷갈리는 개념이라 그 문서와의 차이를 명확히
짚는 데 집중했다.

## 정의

Encryption at rest는 "디스크/DB에 저장되는 동안" 데이터를 암호화해두는 것을 말한다. 핵심은
**되돌릴 수 있다(복호화 가능)**는 점이다 — 올바른 키만 있으면 원래 값을 그대로 복원할 수 있다.
이 점이 [비밀번호 해싱](./Password-Hashing.md)과의 결정적 차이다: 해싱은 의도적으로 되돌릴 수
없게 설계되고(서버는 "일치하는가"만 확인하면 되지 원래 비밀번호를 알 필요가 없다), 암호화는
"나중에 원래 값을 다시 보여줘야 하는" 데이터에 쓴다 — 이름, 주소, 전화번호처럼.

## 요약

"이 값을 나중에 다시 원래대로 보여줘야 하는가?"가 암호화와 해싱을 가르는 질문이다. 그렇다면
암호화(가역), 아니라면(로그인 확인처럼 "일치 여부"만 필요하다면) 해싱(불가역)을 쓴다.

## 상세

### 왜 방명록 이름은 해싱이 아니라 암호화인가

`get_guestbook.php`는 방문자 이름을 화면에 그대로 보여줘야 한다 — "익명123님이 작성"처럼.
해시로 저장했다면 원래 이름을 복원할 방법이 없으므로 이 요구사항 자체를 만족할 수 없다.
그래서 되돌릴 수 있는 암호화가 필요했다.

### AES-256-GCM을 고른 이유

```php
// backend/lib/crypto.php
function encrypt_field(string $plaintext): string
{
    $iv = random_bytes(12); // GCM 표준 96비트 nonce
    $tag = '';
    $ciphertext = openssl_encrypt($plaintext, 'aes-256-gcm', field_encryption_key(), OPENSSL_RAW_DATA, $iv, $tag);
    return 'enc:v1:' . base64_encode($iv . $tag . $ciphertext);
}
```

GCM(Galois/Counter Mode)은 "인증된 암호화(AEAD, Authenticated Encryption with Associated
Data)" 모드다 — 암호화와 동시에 무결성 검증용 태그(`$tag`)를 만든다. 이게 왜 중요하냐면, 옛날
방식인 CBC 모드는 암호화만 하고 "이 암호문이 변조되지 않았는가"는 별도로 확인해야 했는데,
그 확인을 빼먹는 실수(패딩 오라클 공격 등으로 이어짐)가 실무에서 반복적으로 발생했다. GCM은
`openssl_decrypt`에 태그를 같이 넘기면 태그가 안 맞을 때 자동으로 복호화를 실패(`false` 반환)
시켜주므로, "복호화는 됐는데 사실 변조된 값이었다"는 사각지대가 구조적으로 줄어든다.

### nonce(IV)를 매번 새로 만드는 이유

`random_bytes(12)`로 매 암호화마다 새로운 IV(초기화 벡터, GCM에서는 nonce라고도 부른다)를
만든다. 같은 키로 같은 IV를 재사용하면 GCM의 안전성 보장이 깨진다 — 두 암호문을 비교해서 평문에
대한 정보가 새어나갈 수 있다. 그래서 IV는 "비밀"은 아니지만(그래서 암호문과 같이 평문으로
저장해도 안전하다) "절대 재사용하면 안 되는 값"이다. 이 프로젝트는 IV+태그+암호문을 통째로
이어붙여 base64로 인코딩해서 한 컬럼에 저장한다 — 복호화할 때 그 순서 그대로 다시 잘라내 쓴다.

### 레거시 평문과의 공존 — 왜 마이그레이션 스크립트를 안 만들었나

```php
function decrypt_field(string $stored): string
{
    if (strpos($stored, 'enc:v1:') !== 0) {
        return $stored; // 암호화 이전에 저장된 레거시 평문
    }
    // ... 복호화
}
```

암호화를 도입하기 전에 이미 운영 DB에 평문으로 저장된 방명록 이름들이 있다. 이 값들을 일괄
재암호화하는 마이그레이션 스크립트를 짤 수도 있었지만, `enc:v1:` 접두사로 "암호화된 값인지"를
구분할 수 있게 해두면 새/옛 데이터가 같은 컬럼에 섞여 있어도 각자 올바르게 처리된다 — 접두사가
없으면 그냥 그대로 반환한다. 마이그레이션 없이 배포 즉시 하위 호환이 되는 대신, 옛날 데이터는
영원히 평문으로 남는다는 트레이드오프가 있다 — 이 프로젝트처럼 옛 데이터 양이 적고 위험도가
낮은 개인 방명록에서는 합리적인 선택이지만, 규제 대상 개인정보라면 강제 재암호화 배치가
필요했을 것이다.

### 키는 어디에 두나 — 그리고 이게 왜 완전한 해법이 아닌가

암호화 키(`field_encryption_key`)는 `config.local.php`에 base64로 저장된다. 이건 "DB만 유출된
경우"(예: DB 백업 파일이 잘못 노출되거나, DB 서버만 뚫린 경우)를 막아준다 — 공격자가 암호문만
가져가면 키 없이는 원문을 못 읽는다. 하지만 **애플리케이션 서버(파일시스템) 자체가 뚫리면**
`config.local.php`도 같이 읽히므로 이 방어는 무력화된다. 즉 이 암호화는 "DB 유출"과 "서버 전체
장악"을 서로 다른 위협으로 구분해서, 앞의 것만 막아주는 부분적 방어라는 걸 분명히 알아야 한다 —
같은 날 "그럼 `config.local.php` 자체를 암호화하는 건 의미가 있는가"라는 질문도 나왔는데,
결론은 "아니오"였다. 복호화 키를 자동화된 요청 처리 중에 읽으려면 결국 그 키도 서버의 어딘가에
평문으로 있어야 하고, 파일시스템 접근 권한을 가진 공격자에게는 원본 파일을 암호화해도 그 옆의
키 파일까지 같이 노출되므로 보호 효과가 없다 — 이 경우엔 파일 권한(`chmod 600`)처럼 접근 자체를
좁히는 게 실질적인 방어다.

## 비교표

| | 비밀번호 해싱 (`password_hash`) | 필드 암호화 (AES-256-GCM) |
|---|---|---|
| 되돌릴 수 있는가 | 아니오(단방향) | 예(키만 있으면 복원) |
| 서버가 원본 값을 알아야 하나 | 아니오 — 일치 여부만 확인 | 예 — 나중에 원본을 다시 보여줘야 함 |
| 용도 | 로그인 비밀번호 | 이름/주소처럼 화면에 다시 표시해야 하는 개인정보 |
| 키/솔트 유출 시 | 솔트가 유출돼도 각 해시는 여전히 개별 무차별 대입 필요 | 키가 유출되면 암호문 전부 즉시 복호화 가능 |

## 질문

- **Q. 방명록 `message`(작성 내용)는 왜 암호화 안 했나?**
  A. `message`는 애초에 공개 게시판에 누구나 볼 수 있도록 방문자가 스스로 올린 글이다 — DB
  유출 여부와 무관하게 이미 웹사이트에서 공개적으로 노출되는 값이라, 저장 시 암호화가 막아줄
  위협이 없다. 반면 `name`은 짧은 별명/이름으로, 다른 서비스에서 재사용하는 개인 식별 정보일
  가능성이 있어 구분했다.

- **Q. 키를 나중에 바꾸고 싶으면?**
  A. 이 구현은 키 회전을 지원하지 않는다 — 키를 바꾸면 그 전에 암호화된 모든 값이 복호화
  불가능해진다. 진짜 키 회전이 필요하면 옛 키로 복호화 → 새 키로 재암호화하는 배치 작업이
  별도로 필요하다(봉투 암호화(envelope encryption)처럼 "데이터 키"와 "키 암호화 키"를 분리하는
  구조를 쓰면 이 배치 작업 없이도 회전할 수 있지만, 개인 프로젝트 규모에는 과하다고 판단했다).

## 예시 코드

```php
// 저장 시
$encryptedName = encrypt_field($name);
$stmt->bind_param("ss", $encryptedName, $message); // INSERT ...

// 조회 시
$row['name'] = decrypt_field($row['name']);
```

## 플로우차트

이 주제는 [Rate-Limiting.flow.md](./Rate-Limiting.flow.md)처럼 분기가 많은 흐름이 아니라
"암호화 → 저장 → 조회 → 복호화"의 단순한 선형 흐름이라 별도 플로우차트 없이 위 예시 코드로
충분하다고 판단했다.

## 실무

실무에서는 컬럼 단위 애플리케이션 암호화 대신 **DB 자체의 투명한 데이터 암호화(TDE,
Transparent Data Encryption)**를 쓰는 경우도 많다 — MySQL/MariaDB의 InnoDB 테이블스페이스
암호화, AWS RDS의 저장 암호화 등. TDE는 디스크에 물리적으로 접근했을 때(도난, 백업 파일 유출)를
막아주지만, DB 자격증명으로 정상 접속한 쿼리에는 평문이 그대로 보인다 — 즉 "DB 서버가 뚫린 경우"
방어는 애플리케이션 레벨 암호화만큼 강하지 않다. 반대로 애플리케이션 레벨 암호화는 이번처럼
"쿼리 결과 자체는 유출됐지만 애플리케이션 서버까지는 안 뚫린" 시나리오를 막아준다 — 실무에서는
둘을 같이 쓰는 경우가 흔하다(방어 심층화).

## (2026-09-09 갱신) 실제 배포된 백엔드엔 이 암호화가 없다

위 내용은 PHP `backend/lib/crypto.php`에서 실제로 동작하던 구현을 기술한 것이지만, 백엔드가 그
사이 Spring Boot로 완전히 재작성되어 프로덕션에 배포됐고, 새 `GuestbookEntry` 엔티티의 `name`
컬럼은 평문 `VARCHAR(50)` 그대로다 — AES-256-GCM 암호화가 이식되지 않았다.

**(정정, 같은 날) 처음엔 이걸 "이유를 알 수 없는 단순 누락"으로 적었는데, 틀렸다.** 이관을 실제로
수행한 세션의 기록(`DevelopPrompt/CODE_MEMO.md`의 `MEMO-WEB-11`)을 나중에 확인해보니, "암호화는
스키마 변경이 더 큰 별도 작업이라 범위 밖 — 필요해지면 후속 작업으로 남겨둠"이라고 **명시적으로
범위에서 뺀 결정**이었다. CORS 와일드카드가 "다시 생각해보니 원래 안전했다"는 근거가 있는
재확인이었던 것과 마찬가지로, 이것도 근거 없는 방치가 아니라 "이번 이관은 프레임워크 전환으로
범위를 한정한다"는 판단 아래 의도적으로 미룬 항목이다 — 다만 그 사이 방명록 이름은 실제로 평문
그대로 저장되고 있으므로, DB 유출 시 노출된다는 실질적 위험 자체는 CORS 쪽과 달리 그대로 남아있다.
