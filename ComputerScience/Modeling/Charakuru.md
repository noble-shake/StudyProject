  궁금해져서 저장소 구조와 배포 문서(README, 튜토리얼, 이용약관)를 읽고 정리한 기록이다.

## 정의

**Charakuru**는 캐릭터 일러스트 한 장으로 **VRM 아바타**를 만드는 작업을, 사람과 AI 에이전트가
나눠서 진행하도록 묶어 둔 키트다. Nano(ナノ)가 만들었고, AI 3D 생성
서비스인 **Tripo**가 공식 후원한다(README 첫 이미지에 "sponsored by Tripo"가 명시돼 있다).

여기서 쓰이는 용어 몇 가지를 먼저 풀어 둔다.

- **VRM**은 3D 캐릭터 모델을 담는 파일 형식이다. glTF를 기반으로 사람형 뼈대 규격, 표정, 머리카락과
  옷이 흔들리는 물리(spring bone), 그리고 "이 모델을 누가 어떻게 써도 되는지"라는 이용 조건까지
  파일 안에 함께 담는다. VTuber 방송 프로그램이나 VRChat 같은 곳에서 아바타를 옮겨 다닐 수 있게
  해 주는 공통 규격이라고 보면 된다.
- **Tripo**는 이미지 몇 장으로 3D 메시를 만들어 주는 생성형 AI 서비스다. Charakuru는 Tripo의
  Smart Mesh 기능으로 머리와 몸의 3D 후보를 만들고, 파츠 분리·UV 펼치기·텍스처 재생성·리깅까지
  Tripo 안에서 처리한다.
- **리깅**은 3D 모델 안에 뼈대를 넣고, 각 정점이 어느 뼈를 얼마나 따라 움직일지(가중치)를 정하는
  작업이다. 이게 있어야 팔을 들거나 걸을 때 모델이 자연스럽게 휘어진다.
- **Blender MCP**는 AI 에이전트가 Blender라는 3D 프로그램을 직접 조작할 수 있게 이어 주는 연결
  장치다. MCP(Model Context Protocol)는 에이전트가 외부 도구를 부르는 표준 방식이다.

## 요약

이 저장소(`Charakuru`)에는 실행 코드도 스킬 문서도 없고, **배포용 안내 문서와 스크린샷만** 있다.
실제 키트(Node.js로 도는 로컬 앱, 에이전트 진입 문서 `AGENTS.md`, 단계별 스킬 7개, 보조 스크립트)는
원본 저장소의 Releases에 올라오는 전용 ZIP에 들어 있다. 설치 목록이 길어 보이는 이유는 앱이
복잡해서가 아니라, 이미지 생성·Tripo·Blender라는 서로 다른 도구 세 개를 에이전트가 대신
조작하도록 이어 붙인 **작업 파이프라인**이기 때문이다.

## 상세

### 저장소에 있는 것과 없는 것

처음 저장소를 열어 보면 파일이 69개나 되지만, 대부분은 영어·일본어 튜토리얼에 들어가는 스크린샷
이미지다. 나머지는 README, 튜토리얼, 시작 가이드, 이용약관 설명, 이슈 템플릿, 그리고 키트가 쓰는
오픈소스 라이브러리들의 라이선스 원문이다. `public/vendor/` 폴더가 있어서 코드가 있는 것처럼
보이지만, 안에 든 건 three.js 같은 라이브러리의 **라이선스 텍스트**뿐이고 라이브러리 코드 자체는
없다. `SKILL.md`나 `AGENTS.md`도 이 저장소에는 없다.

README가 이 점을 직접 밝힌다. "이 저장소에는 배포 문서와 이미지가 들어 있고, 실행 가능한 앱과 루트의
`AGENTS.md`는 전용 배포 ZIP에 들어 있다." 그래서 GitHub가 자동으로 만들어 주는 "Source code" 압축본을
받으면 문서만 받게 되고, 반드시 Releases의 `charakuru-1.0.2-….zip`을 받아야 한다. 또 하나 주의할
점은 **포크에는 Releases가 복사되지 않는다**는 것이다. `noble-shake/Charakuru`의 Releases는 비어
있으므로 ZIP은 원본 `nanocle/Charakuru`에서 받아야 한다.

README가 설명하는 ZIP의 구성은 다음과 같다.

| 경로 | 역할 |
|---|---|
| `AGENTS.md` | 에이전트의 출발점. 필요한 도구, 단계, 저장 규칙 |
| `public/`, `server.mjs` | 로컬 검토 앱 |
| `skills/` | 단계별 스킬 7개 |
| `scripts/` | 에이전트가 프로젝트 파일을 갱신할 때 쓰는 스크립트 |
| `assets/donor/weighted-body.blend` | 가중치를 옮겨 올 때 쓰는 기본 몸체 |
| `docs/` | 튜토리얼, 미리보기 가이드, 이용약관 설명 |

즉 "스크립트가 있는 저장소냐, 스킬 문서 저장소냐"라는 질문의 답은 **둘 다 ZIP 쪽에 있고, 이
저장소는 그 ZIP을 소개하는 안내판**이라는 것이다.

### 앱은 Node.js로 돈다

로컬 앱은 Node.js 22 이상에서 돈다. 압축을 푼 폴더에서 `npm start`를 실행하면
`http://127.0.0.1:8766`에 검토용 웹 페이지가 뜨고, 평소에는 `npm install`도 필요 없다. 설치 없이
바로 켜진다는 건 필요한 라이브러리를 ZIP 안에 미리 넣어 두었다는 뜻이다. `server.mjs`라는 파일
이름(`.mjs`는 ES 모듈 형식의 JavaScript)과 `THIRD_PARTY_NOTICES.md`에 적힌 라이브러리 목록을
보면 구조를 짐작할 수 있다.

- **three.js**: 브라우저에서 3D를 그리는 라이브러리. 모델 후보를 돌려 보고 와이어프레임을 켜는
  화면이 이걸로 그려진다.
- **three-vrm / three-vrm-animation**: three.js 위에서 VRM 모델을 읽고, VRMA(VRM용 모션 파일)를
  재생하는 확장. 완성된 아바타를 미리보기에서 걷게 하고 머리카락 물리를 켜 보는 부분이다.
- **fflate**: 브라우저와 Node 양쪽에서 쓰는 압축 라이브러리. 프로젝트 전체를 담는 단일 파일
  `project.charakit`을 읽고 쓰는 데 쓰이는 것으로 보인다.

정리하면 Node는 로컬 서버와 파일 저장을 맡고, 화면은 브라우저에서 three.js로 그리는 평범한 로컬 웹앱
구조다. 다만 코드는 직접 보지 않았으므로 서버가 정확히 어떤 일을 하는지는 아직 확인하지 못했다.

### 설치 목록이 긴 이유: 앱이 아니라 파이프라인이 복잡하다

README의 준비물 표에는 Node.js, Chromium 계열 브라우저, 이미지 생성과 브라우저 조작이 되는 Codex,
로그인된 Tripo 계정, Blender 5.2, VRM Add-on for Blender, Blender MCP가 나란히 적혀 있다. 처음 보면
"무슨 앱이길래 이렇게 많이 깔아야 하나" 싶지만, 앱 자체는 위에서 본 것처럼 `npm start` 한 번이면
켜진다. 목록이 긴 건 키트가 하려는 일이 원래 여러 프로그램을 거쳐야 하는 일이기 때문이다.

캐릭터 일러스트를 3D 아바타로 만드는 작업은 보통 이렇게 진행된다. 먼저 캐릭터를 여러 방향에서 본
그림이 필요하다. 그 그림으로 3D 형태를 만들고, 파츠를 나누고, 텍스처를 입힌다. 그다음 뼈대를 넣고
가중치를 다듬고, 머리카락과 치마가 흔들리게 물리를 설정한 뒤, VRM으로 내보낸다. 사람이 이걸 직접
하려면 Blender를 꽤 깊이 배워야 한다. Charakuru의 발상은 **"사람이 Blender를 배우는 대신, AI가
Blender를 조작할 수 있는 환경을 갖춘다"**는 것이다. 그러려면 다음이 필요해진다.

- Blender는 데스크톱 프로그램이므로, 에이전트가 조작하려면 Blender MCP라는 연결 장치를 따로 깔아야
  한다. VRM으로 내보내려면 VRM 애드온도 필요하다.
- Tripo는 API가 아니라 **사용자가 로그인해 둔 브라우저를 에이전트가 직접 조작**하는 방식으로 쓴다.
  그래서 에이전트에 브라우저 조작 기능이 있어야 하고, 키트는 새 브라우저를 띄우기보다 이미 열린
  브라우저와 탭을 재사용하라는 규칙(`docs/browser-use.md`)까지 따로 둔다.
- 이미지 생성과 Tripo는 각자 본인 계정과 요금으로 쓴다. Tripo 크레딧은 3D 후보를 만드는
  단계부터 소모된다.

### 다섯 번의 체크포인트

작업은 다섯 번의 "사람이 확인하고 → 에이전트에게 넘기는" 왕복으로 진행된다.

1. **일러스트 불러오기 → 8장 요청.** 사람이 일러스트를 앱에 넣으면, 에이전트가 머리(머리카락 포함)와
   몸을 앞·왼쪽·오른쪽·뒤 네 방향씩 다시 그려 8장을 만든다. 머리는 입을 다문 차분한 표정으로, 몸은
   팔을 옆으로 벌린 T-포즈로 그린다.
2. **8장 검토 → 3D 후보 생성.** 사람이 8장을 확인하고 이상한 장만 골라 수정을 요청할 수 있다. 확정하면
   에이전트가 Tripo에서 머리와 몸의 3D 후보를 네 개씩 만든다.
3. **후보 선택 → 파츠·텍스처 정리.** 사람이 후보를 돌려 보며 머리 하나, 몸 하나를 고른다. 에이전트는
   Tripo에서 파츠를 나눠 얼굴·머리카락·옷으로 분류하고, UV를 펼쳐 텍스처를 4K로 다시 만든다.
4. **비율 조정 → 리깅과 물리.** 사람이 머리 크기, 목 연결, 전체 키를 맞춘다. 에이전트는 Tripo에서
   리깅한 뒤 뼈 위치만 가져오고, 키트에 들어 있는 기본 몸체에서 가중치를 옮겨 온다. 그다음 머리카락을
   다시 붙이고 흔들리는 부분의 물리를 설정한다.
5. **동작 확인 → VRM 내보내기.** 사람이 걷기 모션으로 어깨·팔꿈치·무릎이 제대로 굽는지 본다. 확정하면
   에이전트가 모델 이름, 작성자, 이용 조건을 묻고 `exports/avatar.vrm`과 편집용 `avatar.blend`를
   내보낸 뒤, 내보낸 VRM을 다시 읽어 물리가 실제로 움직이는지 확인한다.

이 구조의 핵심은 **에이전트가 체크포인트를 혼자 넘어가지 않는다**는 점이다. 후보를 고르는 것 같은
눈으로 판단할 일은 언제나 사람이 하고, 파일을 나누고 정리하고 내보내는 반복 작업은 에이전트가 한다.

### 사람과 에이전트가 바통을 넘기는 방법

앱과 에이전트는 서로 직접 대화하지 않는다. 각 단계의 "계속" 버튼을 누르면 앱이 요청문을 보여 주고,
사람이 그걸 복사해서 Codex 채팅에 붙여 넣어 보낸다. **복사만 해서는 에이전트가 시작하지 않는다.**
요청문 안에는 `agent-session.mjs begin` 같은 시작 명령이 들어 있어서, 에이전트가 이걸 실행하면 앱의
현재 상태가 저장되고 작업이 시작된다. 에이전트가 일을 마치면 앱이 스스로 새 상태로 바뀌고 다음
체크포인트에서 멈춘다.

이 방식 덕분에 사람이 파일을 내보내고 다시 불러오는 일이 없다. 프로젝트는 `project.charakit`
하나에 저장되고, 같은 폴더에서 앱을 다시 켜면 마지막 상태가 그대로 열린다. 날짜가 붙은 사본이나
"final2" 같은 파일이 쌓이지 않게 하려는 설계다.

### 단계별 스킬 7개

에이전트는 `AGENTS.md`로 전체 흐름을 파악하고, 단계마다 해당 스킬을 따라 일한다.

| 스킬 | 맡는 일 |
|---|---|
| `charakit-project` | 프로젝트 파일 확인·읽기·갱신 |
| `character-parts-images` | 머리와 몸 4방향씩 8장 그리기 |
| `character-material-brushup` | 디자인을 바꾸지 않고 그림과 재질 다듬기 |
| `tripo-agent-workflow` | Tripo 후보 생성, 파츠 분류, UV와 텍스처 재생성, 리깅 |
| `avatar-weight-transfer` | 흔들리는 파츠 분리, 기본 몸체에서 가중치 옮기기 |
| `avatar-spring-setup` | 머리카락·옷 물리, VRM 내보내기와 검사 |
| `tripo-character-setup` | 사람이 관절 표시를 직접 찍는 정밀 리깅(선택했을 때만) |

### 눈에 띄는 점

- **Windows Codex에서 `start` 명령이 막히는 문제.** 예전 요청문은 `agent-session.mjs start URL ID`
  형태였는데, Windows의 Codex가 `start`와 URL 조합을 PowerShell의 URL 실행으로 오인해 정책상
  차단했다. 키트는 명령 이름을 `begin`으로 바꿔 이 오탐을 피했다. 에이전트 도구의 안전 검사가
  명령 이름과 인자를 구분하지 않아서 생긴 문제로, 에이전트용 CLI를 설계할 때 동사 하나도 조심해서
  골라야 한다는 사례다.
- **현재 한계.** 새로 만든 캐릭터는 표정 변화와 시선 움직임이 없는 중립 얼굴이다. 앱 안의 걷기
  확인은 뼈와 피부 변형만 보여 주고, 물리는 내보낸 VRM에서만 확인할 수 있다. UI는 영어와 일본어를
  지원하지만 에이전트에게 넘기는 요청문은 항상 일본어다.
- **라이선스는 오픈소스가 아니다.** "source-available" 방식으로, 비상업·상업 용도 모두 쓸 수 있지만
  키트를 재배포하거나 다른 제품에 넣으려면 미리 연락해야 하고, 번들 자산만 따로 빼 가는 것은
  금지다. 사업 전체의 연 매출과 누적 투자가 **둘 다 1억 엔 미만**이면 별도 계약 없이 쓸 수 있고,
  하나라도 넘으면 서면 계약이 필요하다. Pull Request는 받지 않는다.

|---|---|---|---|---|
| 필요한 3D 지식 | 거의 없음 | 많음 (모델링·리깅·가중치) | 적음 | 없음 |
| 결과 품질 통제 | 체크포인트 5번에서 사람이 판단 | 완전 통제 | 생성 결과에 의존 | 통제가 어려움 |
| 리깅·물리·VRM 내보내기 | 에이전트가 처리 | 직접 | 리깅까지만, 마무리는 별도 | 에이전트 판단에 맡김 |
| 준비물 | 많음 (Codex, Tripo, Blender, MCP 등) | Blender | Tripo 계정 | 에이전트 환경 |
| 비용 | Tripo 크레딧 + 이미지 생성 + 에이전트 | 시간 | Tripo 크레딧 | 에이전트 사용량 |

README는 이 위치를 "에이전트에게 전부 맡기는 것보다 현실적이고, 전부 손으로 하는 것보다 쉬운 균형"이라고
설명한다.

## 질문

- **Q. 이 저장소는 스크립트 저장소인가, 스킬 문서 저장소인가?**
  A. 둘 다 아니다. 배포 안내 문서와 스크린샷만 있다. 스크립트(`scripts/`, `server.mjs`)와 스킬
  7개(`skills/`), `AGENTS.md`는 전부 Releases의 배포 ZIP에 들어 있다.

- **Q. Node.js로 만든 앱인가?**
  A. 로컬 검토 앱은 Node.js 22 이상에서 돌고 `npm start`로 켜진다. 화면은 브라우저에서 three.js와
  three-vrm으로 그린다. 하지만 3D를 만드는 일 자체는 앱이 아니라 에이전트가 Tripo와 Blender를
  조작해서 한다. 앱은 지금 어느 단계인지 보여 주고, 사람이 고르게 하고, 다음 요청문을 만들어 주는
  관제탑 역할이다.

- **Q. 왜 이렇게 설치할 게 많은가?**
  A. 일러스트에서 VRM까지 가는 길에 이미지 생성, Tripo, Blender라는 서로 다른 도구 세 개가 필요하고,
  사람 대신 에이전트가 그 도구들을 조작하려면 각 도구마다 연결 장치(브라우저 조작, Blender MCP)가
  필요하기 때문이다.

- **Q. 포크한 저장소에서 ZIP을 받을 수 있나?**
  A. 없다. 포크에는 Releases가 복사되지 않는다. 원본 `nanocle/Charakuru`의 Releases에서 받는다.

## 예시 코드

키트를 시작할 때 에이전트에게 보내는 첫 요청이다. 배포 ZIP을 푼 폴더를 Codex로 열고 보낸다.

```text
Read the root AGENTS.md and help me start creating a character with this kit.
```

에이전트 없이 앱만 직접 켤 때는 같은 폴더에서 다음을 실행하고 `http://127.0.0.1:8766`을 연다.
`npm install`은 필요 없다.

```bash
npm start
```

## 실무

- 일러스트에서 3D 캐릭터를 만드는 일은 실무에서 원화가, 모델러, 리거가 나눠 맡는 분업 작업이다.
  Charakuru는 이 중 모델러와 리거 몫의 반복 작업을 에이전트에게 넘기고, 판단만 사람에게 남기는
  방식이다. 개인 VTuber나 인디 개발자처럼 3D 인력이 없는 경우에 맞다.
- 같은 목적의 흔한 대안으로는 VRoid Studio(애니메 스타일 캐릭터를 처음부터 직접 만드는 무료
  도구)와, 외주 모델러에게 맡기는 방법이 있다. VRoid는 기존 일러스트를 그대로 옮기기 어렵고, 외주는
  비용과 시간이 든다.
- 2026년 기준 동향: 이미지에서 3D를 생성하는 서비스(Tripo 등)와, 데스크톱 3D 도구를 MCP로 조작하는
  에이전트가 함께 쓰이기 시작했다. Charakuru는 이 둘을 "사람이 체크포인트에서 판단한다"는 규칙으로
  묶은 사례다. 키트 자체도 아직 개발 중이라 문서가 실제 동작을 다 따라가지 못한다고 밝히고 있다.
