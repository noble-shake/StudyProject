  남길 수 있는가, 데이터가 커지면 어떻게 되는가)을 정리한 기록이다.

## 정의

`DevelopPrompt`는 여러 AI 에이전트(Claude Code, Codex 등)가 함께 참조하는 개인 개발 규약집이다.
규약을 아무리 잘 써 두어도, 에이전트가 실제로 그 문서를 읽는지는 따로 확인하지 않으면 알 수 없다.
**규약 참조 애널리틱스**는 이 질문에 답하기 위한 작은 도구다. 에이전트가 어떤 규약 파일을 읽었는지,
그 다음 어느 폴더로 이동했는지, 한 번도 읽히지 않은 규약은 무엇인지를 모아서 로컬 웹 페이지에
보여준다.

여기서 "애널리틱스"는 웹사이트 방문자 분석과 같은 발상이다. 웹 애널리틱스가 "사람이 어떤 페이지를
보고 어디로 이동했는가"를 보듯이, 이 도구는 "에이전트가 어떤 규약을 보고 어디로 이동했는가"를 본다.
방문자 대신 도구 호출(Read, Grep 등)이 이벤트가 된다.

## 요약

에이전트가 남기는 대화 기록 파일(트랜스크립트)을 서버가 **새로 붙은 줄만** 계속 읽어서 공통 이벤트로
바꾸고, 이를 분석해 `127.0.0.1`에서만 열리는 대시보드로 보여준다. 파일 내용은 저장하지 않고
"어떤 파일의 몇 번째 줄부터 몇 번째 줄까지, 어느 절을 읽었는가"라는 메타데이터만 다루기 때문에
가볍고, 대화 기록이 수백 MB로 커져도 갱신 한 번에 수십 ms면 끝난다.

## 상세

### 왜 만들었나

규약집은 "에이전트가 세션을 시작하면 README → 팀 규칙 우선순위 → 세션 시작 규칙 순서로 읽는다"는
식의 진입 경로를 정해 둔다. 그런데 이 경로가 실제로 지켜지는지는 감으로만 알 수 있었다. 이 도구로
처음 확인해 보니, DevelopPrompt를 연 세션 25개 중 README를 Read 도구로 읽은 세션은 10개뿐이었다.
셸 명령(`cat`, `sed`, `git show`)으로 읽은 경우까지 합치면 약 20개였고, 5개 세션은 README를 아예
건너뛰고 브랜치 규칙이나 프로젝트 폴더로 바로 들어갔다.

이 결과는 두 가지를 알려 준다. 하나는 **측정의 한계**다. 도구가 Read·Glob·Grep·Edit·Write만 세기
때문에, 셸로 읽은 것은 보이지 않는다. 다른 하나는 **실제 행동**이다. "읽으라"는 지시만으로는
에이전트가 진입 문서를 건너뛸 수 있다. 그래서 세션 시작 hook이 README의 핵심 절을 아예 맥락에 직접
넣도록 바꿨다. 측정이 행동을 바꾼 사례다.

### 전체 구조 — 수집, 정규화, 분석, 서버, 화면

도구는 다섯 단계로 나뉘고, 각 단계가 파일 하나씩을 맡는다. 단계 사이는 "공통 이벤트"라는 하나의
데이터 형식으로만 이어진다. 이렇게 하면 수집 방법이 바뀌어도(예: Codex 어댑터 추가) 뒤 단계는
손대지 않아도 된다.

1. **수집** — 데이터가 들어오는 길은 두 가지다.
   - **트랜스크립트 파싱**: Claude Code는 대화를 `~/.claude/projects/**/*.jsonl`에 한 줄에 메시지
     하나씩 계속 덧붙여(append) 쓴다. 이 파일에는 에이전트가 호출한 도구와 그 입력값(어느 파일을,
     몇 번째 줄부터)이 이미 들어 있다. 따라서 따로 설치할 것 없이 이 파일만 읽으면 된다.
   - **PostToolUse hook** (`log_tool_use.py`): Claude Code의 hook 기능으로, 도구 호출이 끝날 때마다
     작은 스크립트를 실행해 이벤트 한 줄을 별도 로그에 남긴다. 기록하는 순간의 파일 상태를 볼 수
     있다는 장점이 있다.
2. **정규화** (`events.py`) — 두 경로의 데이터를 같은 모양의 이벤트(누가, 언제, 어떤 도구로, 어떤
   파일의, 어느 범위를)로 맞춘다. 같은 세션에 hook 이벤트가 있으면 트랜스크립트 이벤트는 버려서 중복을
   막는다.
3. **분석** (`analyze.py`) — 이벤트를 모아 규약 파일별 참조 횟수, "규약을 읽은 뒤 15분 안에 어느
   폴더로 이동했는가"라는 전이, 읽고 나서 아무 데도 안 간 경우, 한 번도 안 읽힌 규약, 절별 부분 읽기
   횟수를 계산해 JSON 하나로 내보낸다.
4. **서버** (`serve.py`) — 파이썬 표준 라이브러리의 `http.server`로 `127.0.0.1`에서만 열린다. 외부에
   노출되지 않으므로 인증이 필요 없다. 페이지가 `/api/report`를 요청하면 분석 결과를 돌려준다.
5. **화면** (`dashboard.html`, `topology.js`) — 외부 라이브러리 없이 SVG로 저장소 폴더 트리를 그리고,
   새 접근이 들어오면 에이전트 노드에서 대상 파일까지 빛 점(패킷)이 이동하는 애니메이션을 보여준다.

### 실시간 반영은 어떻게 되는가

"실시간"은 거창한 기술이 아니라 세 가지 단순한 장치의 조합이다.

첫째, Claude Code가 트랜스크립트 파일에 **작업하는 동안 계속** 줄을 덧붙인다. 즉 원천 데이터가 이미
실시간으로 쌓이고 있다.

둘째, 서버는 결과를 1초 동안 재사용(캐시)하고, 페이지는 3초마다 결과를 다시 요청(폴링)한다. 그래서
에이전트가 파일을 읽고 나서 몇 초 안에 화면에 나타난다. 처음에는 5초 캐시와 10초 폴링이라 최대 15초가
걸렸는데, 아래의 증분 읽기 덕분에 한 번 갱신하는 비용이 수십 ms로 줄어서 주기를 짧게 당길 수 있었다.
웹소켓 같은 푸시 방식이 아니라 폴링을 쓴 이유는 단순함 때문이다. 서버 코드가 몇십 줄로 끝난다.
브라우저는 숨겨진 탭의 타이머를 크게 늦추므로, 탭이 다시 보이는 순간(`visibilitychange`) 바로 한 번
갱신하게 했다.

셋째, 그리고 가장 중요한 것이 **증분 읽기**다. 처음 버전은 요청마다 트랜스크립트 전체(약 328MB,
파일 49개)를 처음부터 다시 읽었고, 한 번에 1.8초가 걸렸다. 5초마다 1.8초씩 CPU를 쓰는 셈이다.
지금은 파일마다 "어디까지 읽었는지"(바이트 위치, offset)를 기억해 두고, 다음 요청에서는 그 뒤에 새로
붙은 부분만 읽는다. 결과적으로 두 번째부터는 한 번에 약 0.02초로 줄었다.

증분 읽기에는 세 가지 세부 처리가 필요했다.

- **아직 쓰는 중인 마지막 줄은 남겨 둔다.** 파일을 읽는 순간 Claude Code가 줄을 반쯤 쓰고 있을 수 있다.
  그래서 마지막 줄바꿈 문자까지만 처리하고, 그 뒤 조각은 다음 번에 다시 읽는다.
- **파일이 줄어들면 처음부터 다시 읽는다.** 기억해 둔 위치보다 파일이 작아졌다면 파일이 새로 쓰였다는
  뜻이므로 위치를 0으로 되돌린다.
- **필요 없는 줄은 파싱하지 않는다.** 트랜스크립트의 대부분은 파일 내용이나 명령 출력 같은 큰 줄이다.
  JSON을 풀기 전에 그 줄에 `"tool_use"`라는 글자가 있는지 바이트 단위로 먼저 확인하고, 없으면
  건너뛴다. 이것만으로 첫 로드가 1.8초에서 1.2초로 줄었다.

여기에 더해, 새 이벤트가 하나도 없으면 분석 단계 자체를 건너뛰고, `git ls-files` 같은 비싼 조회는
60초 동안 결과를 재사용한다.

### "무엇을 읽었는가"까지 남기기 — 줄 범위와 절

파일 이름만으로는 "README를 읽었다"까지만 알 수 있다. 규약 문서는 길기 때문에 실제로는 "README의 어느
절을 읽었는가"가 더 궁금하다. 이를 위해 이벤트에 두 필드를 더했다.

- **`range`** — 읽은 줄 범위. Read 도구의 입력에 `offset`(시작 줄)과 `limit`(줄 수)이 있으면 그것으로
  `[시작, 끝]`을 만든다. 둘 다 없으면 파일 전체를 읽은 것이므로 비워 둔다.
- **`section`** — 그 범위가 걸친 마크다운 제목(`#`~`###`) 목록. 코드 블록 안의 `#`은 제목으로 치지
  않는다.

여기서 중요한 함정이 하나 있다. 규약 파일은 계속 고쳐진다. 몇 주 전 이벤트의 "40~69번째 줄"을 오늘
파일의 제목에 맞추면 엉뚱한 절이 나올 수 있다. 그래서 두 경우를 구분한다. hook으로 수집한 이벤트는
**기록하는 순간의 파일**에서 절 제목을 뽑아 함께 저장하므로 정확하다. 트랜스크립트에서 나중에 뽑은
이벤트는 지금 파일에 맞춘 값이라 화면에 '추정'으로 표시한다.

반대로 **파일 내용 자체는 절대 저장하지 않는다.** 내용을 저장하면 데이터가 급격히 커지고, 업무용
코드 같은 민감한 내용이 로그에 남는다. 나중에 이 데이터를 다른 서버로 보낼 계획도 있으므로 더욱 그렇다.
"어디를 읽었는가"는 줄 번호와 제목만으로 충분히 표현된다.

### 질문 하나가 어떤 문서를 봤는가 — turn

에이전트는 사용자 질문 하나에 문서를 여러 개 읽는다. 처음에는 "마지막으로 읽은 파일 하나"만 강조했기
때문에, 그 질문에서 무엇을 봤는지는 재생 버튼을 눌러 흐름을 다시 봐야만 알 수 있었다.

트랜스크립트에는 사용자가 보낸 질문도 한 줄씩 들어 있다. 내용이 문자열이고, 메타 줄이나 슬래시 명령 줄이
아닌 `user` 줄이 바로 질문 경계다. 이 줄들을 모아 두고, 모든 이벤트에 "같은 세션에서 그 시각 바로 앞의
질문"을 `turn`으로 붙인다(정렬된 질문 시각 목록에서 이진 탐색). 이렇게 하면 질문 정보가 없는 서브에이전트
기록이나 hook 이벤트도 같은 규칙으로 질문에 묶인다. 분석 결과에는 가장 최근 규약 접근이 속한 질문의 접근
목록(`last_query`)을 따로 담고, 화면은 그 문서들을 한꺼번에 노란 테두리로 강조한다.

### 화면 설계 — 무엇을 보여주고 무엇을 숨기나

화면은 "지금 무슨 일이 일어나는가"에 집중하도록 바뀌었다.

- **전체 화면 Topology.** 폴더 트리가 화면 전체를 쓴다. 통계, 로그, 표 목록은 화면 맨 아래 띠에 마우스를
  대면 올라오는 오버레이에 넣었다. 평소에는 흐름만 보고, 숫자가 필요할 때만 꺼내 보는 구조다.
- **지도처럼 움직이는 화면.** 처음에는 트리 전체가 화면에 맞춰 축소되어 보인다. SVG 자체는 항상 화면
  크기로 두고, 실제로 보이는 영역은 `viewBox`(SVG 좌표계의 사각형)로 정한다. 좌클릭으로 끌면 끈 픽셀만큼
  `viewBox`의 위치를 반대로 옮기고, 휠을 굴리면 커서 아래 지점을 고정한 채 `viewBox`의 크기를 바꾼다.
  이 계산이 간단해지도록 `viewBox`의 가로세로 비율을 항상 화면 비율과 같게 맞춘다 — 그러면 "화면 1px =
  `viewBox` 너비 ÷ 화면 너비"로 바로 환산된다. 4px 넘게 움직였을 때만 드래그로 보고, 그때는 직후의 클릭을
  막아서 폴더가 실수로 펼쳐지지 않게 한다.
- **깊이와 카테고리를 색으로 구분.** 테두리·배경·연결선은 폴더 깊이별 색을 쓰고, 테두리 진하기는 그대로
  접근 빈도를 나타낸다. 글자색은 첫 번째 깊이(`POLICY`, `Unity`, `Web`처럼 규약의 큰 분류)를 따른다. 그래서
  깊은 곳의 파일 하나만 봐도 어느 분류에 속하는지 알 수 있다.
- **처음 열 때 재생하지 않는다.** 예전에는 페이지를 열면 최근 12건을 자동으로 재생했다. 지금은 로그창만
  채우고 실시간 이벤트만 띄운다. 지난 흐름이 보고 싶으면 오버레이에서 건수를 입력해 재생한다.
- **전이 위치 따라가기.** 새 이벤트가 들어오면 그 노드가 화면 가운데에 오도록 스크롤한다. 노드 위에서
  툴팁을 읽는 동안에는 화면이 움직이면 곤란하므로 따라가기를 잠시 멈춘다.
- **마지막으로 읽은 곳만 강조 유지.** 패킷이 도착하면 노드가 잠깐 빛났다가 원래대로 돌아오는데, 가장
  마지막으로 읽힌 노드 하나만은 노란 테두리를 계속 유지한다. 화면을 잠시 떠났다 돌아와도 "마지막에
  어디였는지"를 바로 알 수 있다.
- **마지막 질문 강조와 반복 재생.** 마지막 질문에서 읽은 문서 전체가 노란 테두리로 함께 강조되고, 그중
  마지막 문서가 가장 굵다. 진행 중인 패킷이 없으면 그 질문의 경로 전체를 **동시에** 흘려보내고, 1.2초 쉰 뒤
  다시 반복한다. 처음에는 읽은 순서대로 하나씩 흘렸는데, 그러면 마지막 하나만 눈에 남아 "이 질문이 무엇을
  봤는지"를 한눈에 볼 수 없었다. 이 반복 재생은 로그나 화면 위치, 강조 대상을 바꾸지 않는 "조용한"
  재생이라 실제 이벤트와 섞이지 않는다. 강조 위치는 애니메이션이 끝나길 기다리지 않고 데이터가 도착하는
  즉시 옮긴다 — 숨은 탭에서는 애니메이션이 멈추기 때문이다.
- **패킷은 선과 같은 곡선을 탄다.** 간선은 부모 노드의 오른쪽 끝에서 자식 노드의 왼쪽 끝으로 그려진다.
  처음 버전의 패킷은 부모의 왼쪽 끝에서 출발해서, 같은 모양이지만 다른 위치의 곡선을 따라가는 바람에
  선과 어긋나 보였다. 지점마다 "들어오는 x"(왼쪽 끝)와 "나가는 x"(오른쪽 끝)를 따로 두고, 그리기와
  애니메이션이 같은 끝점과 같은 베지어 제어점을 쓰게 해서 맞췄다.

### 실행 방법

| 방법 | 하는 일 |
|---|---|
| 바탕화면 `DevelopPrompt Dashboard.cmd` | 서버가 떠 있으면 브라우저만 연다. 없으면 `I:\Workspace\DevelopPrompt`에서 "DevelopPrompt Analytics"라는 최소화 창으로 서버를 띄운 뒤 연다. 그 창을 닫으면 서버가 꺼진다. |
| 직접 실행 | `python TOOLS/analytics/serve.py --config-dir <설정 폴더>` 후 `http://127.0.0.1:8765/` |
| 터미널 보기 | `python TOOLS/analytics/term.py --config-dir <설정 폴더> --watch 5` — 같은 분석을 표로 출력하고, 새 이벤트가 있을 때만 다시 그린다 |
| hook 설치(선택) | `python TOOLS/analytics/install_hook.py --config-dir <설정 폴더>`로 바뀔 내용을 먼저 보고, `--apply`로 적용 |

hook은 지금 설치하지 않은 상태다. 측정해 보니 hook 한 번에 약 80ms가 걸렸고, 대부분 파이썬을 새로
띄우는 비용이었다. 파일 읽기 도구를 쓸 때마다 80ms가 붙는 대신 절 정보가 정확해지는 거래인데, 지금은
트랜스크립트만으로도 실시간 확인이 되고 '추정' 절 정보로 충분하다고 판단해 보류했다.

### 개발 방법 — 공용 도구를 어떻게 고쳤나

이 도구는 모든 프로젝트가 함께 쓰는 공용 도구라서, DevelopPrompt의 브랜치 규칙을 따른다.

1. `main`에서 작업 브랜치(예: `claude/analytics-fullscreen`)를 별도 worktree로 만든다. 작업 중인 다른
   체크아웃의 파일을 건드리지 않기 위해서다.
2. 바꾸기 전에 먼저 **측정**한다. 증분 읽기도 "1.8초"라는 숫자를 본 뒤에 시작했다.
3. 바꾼 뒤에는 다시 측정하고(0.02초), JS는 `node --check`로 문법을 검사하고, 실제 브라우저에서
   스크롤 위치와 강조 상태를 확인한다. hook은 `DP_ANALYTICS_DIR`로 출력 폴더를 임시 폴더로 돌려서
   시험 입력을 넣어 본다.
4. 커밋 메시지는 `🔨[Feat]: …` 같은 깃모지 형식으로 쓰고, `main`에 반영한 뒤 활성 `epic/*` 브랜치에도
   병합해서 모든 프로젝트가 같은 도구를 쓰게 한다.

## 질문

- **Q. 대시보드에서 README 횟수가 생각보다 적은 이유는?**
  A. 두 가지가 섞여 있다. 셸 명령으로 읽은 것은 세지 않아서 실제보다 낮게 나오고, 실제로도 일부
  세션은 README를 건너뛴다. 셸 읽기까지 합치면 25개 중 약 20개 세션이 읽었다.

- **Q. 처음 테스트에서 스크롤이 0에서 움직이지 않았던 이유는?**
  A. 자동화 브라우저의 탭이 숨겨진 상태(`document.hidden`)였기 때문이다. 브라우저는 보이지 않는 탭의
  부드러운 스크롤(`behavior: 'smooth'`) 애니메이션을 진행하지 않는다. 그래서 숨은 탭에서는 즉시
  이동(`'auto'`)하도록 했다.

- **Q. 화면 전체가 Topology가 되자 왜 따라가기 멈춤 조건을 바꿔야 했나?**
  A. 원래는 "마우스가 Topology 영역 위에 있으면 멈춤"이었다. 영역이 화면 전체가 되면 마우스는 거의
  항상 그 위에 있으므로 따라가기가 사실상 영원히 멈춘다. 그래서 "노드 툴팁을 보는 동안만 멈춤"으로
  바꿨다.

- **Q. 애니메이션이 선 위를 정말 따라가는지 어떻게 확인했나?**
  A. 눈으로 보는 대신 수치로 확인했다. 애니메이션 중에 패킷 원의 좌표를 여러 번 뽑고, SVG 경로의
  `isPointInStroke()`로 그 점이 실제 간선 위에 있는지 검사했다(검사하는 동안만 선 두께를 4px로
  넓혀서). 고친 뒤에는 12번 뽑아 12번 모두 선 위에 있었다.

- **Q. 세션 도중에 hook을 설치하자 그 세션 기록이 거의 다 사라진 이유는?**
  A. hook 로그와 트랜스크립트가 같은 호출을 두 번 세지 않도록, 처음에는 "hook 이벤트가 하나라도 있는 세션은
  트랜스크립트 이벤트를 버린다"는 세션 단위 규칙을 썼다. 세션 중간에 hook이 켜지면 설치 전 기록은 hook에
  없으니 통째로 사라진다. 두 경로 모두 도구 호출마다 고유한 `tool_use_id`를 갖고 있으므로, 같은 ID만
  골라 버리는 호출 단위 규칙으로 바꿨다.

- **Q. hook이 Windows에서 한글 경로를 깨뜨린 이유는?**
  A. 파이썬은 Windows에서 표준 입력을 시스템 기본 인코딩(cp949)으로 읽는다. Claude Code는 hook에
  UTF-8 JSON을 넘기므로 한글이 깨진다. 표준 입력을 바이트로 받아 직접 UTF-8로 풀도록 고쳤다.

## 예시 코드

증분 읽기의 핵심이다. 파일마다 읽은 바이트 위치를 기억해 두고, 새로 붙은 부분 중 줄바꿈으로 끝난
완결된 줄만 처리한다.

```python
def _tail(path, parse):
    size = path.stat().st_size
    c = _cache.get(path)
    if c is None or size < c["offset"]:        # 처음 보거나 파일이 줄었으면 처음부터
        c = _cache[path] = {"offset": 0, "events": []}
    if size > c["offset"]:
        with open(path, "rb") as f:
            f.seek(c["offset"])
            chunk = f.read(size - c["offset"])
        end = chunk.rfind(b"\n")
        if end >= 0:                            # 아직 쓰는 중인 마지막 줄은 다음 번에
            for raw in chunk[:end].split(b"\n"):
                c["events"].extend(parse(raw))
            c["offset"] += end + 1
    return c["events"]
```

전이 위치 따라가기는 노드 좌표에서 화면 절반을 빼서 스크롤 위치를 정하는 한 줄이 전부다.

```js
stage.scrollTo({
  left: n.x + NODEW / 2 - stage.clientWidth / 2,
  top: n.cy - stage.clientHeight / 2,
  behavior: document.hidden ? 'auto' : 'smooth',
});
```

## 실무

- 로그 파일을 "어디까지 읽었는지" 기억하며 뒤에 붙는 줄만 읽는 방식은 실무 로그 수집기의 기본
  구조다. Fluent Bit, Filebeat 같은 수집기도 파일별 읽은 위치를 따로 저장해 두고 이어 읽는다. 이 도구는
  그 위치를 메모리에만 두기 때문에 서버를 다시 켜면 첫 로드를 한 번 더 한다는 점이 다르다.
- 규모가 커지면 보통 수집(에이전트) → 저장(시계열 DB나 로그 저장소) → 시각화(Grafana 등)로 나눈다.
  이 도구는 개인 머신 하나, 이벤트 수천 건 규모라서 세 단계를 프로세스 하나에 넣었다. 여러 컴퓨터의
  로그를 합치거나 외부 서버로 보내게 되면 그때 저장 단계를 분리하는 것이 자연스럽다.
- 폴링 대신 Server-Sent Events나 웹소켓으로 바꾸면 지연이 줄지만, 지금은 15초 지연이 문제가 되지
  않아 단순한 폴링을 유지한다.
