## 출처

[톤 매핑](../Graphics/Tone-Mapping.md)을 정리하던 중, Unity URP의 `Post Process Data` 에셋을 프레임
디버거로 열어봤을 때 **`Lut Builder Ldr PS`**·**`Lut Builder Hdr PS`**(`UberPost` 등 여러
내부 셰이더와 함께)가 참조돼 있는 걸 발견하고, 그중 톤 매핑과 가장 직접적으로 연결된 이 둘부터
별도 문서로 정리한 것. 나머지 셰이더(Uber PS 등)는 추후 별도 문서로 다룰 예정.

## 정의

**LUT(Look-Up Table)**은 "미리 계산해둔 값들을 담은 표"를 뜻한다. 이 문서에서 다루는 "LUT PS"는
프레임 디버거에 정확히 **`Lut Builder Ldr PS`**와 **`Lut Builder Hdr PS`**로 표시되는 두 패스를
가리킨다 — 이름의 `PS`는 픽셀 셰이더(Pixel Shader) 스테이지를 뜻하는 접미사이고, 소스 상으로는
각각 `LutBuilderLdr.shader`/`LutBuilderHdr.shader`에 대응한다. 이 셰이더는 URP가 색 보정
(화이트 밸런스, 채도, 커브, 채널 믹서 등)과 톤 매핑 곡선을 매 픽셀마다 실시간으로 계산하는 대신,
그 전체 변환을 **작은 3D 텍스처 하나(보통 32×32×32)에 미리 구워 넣는** 역할을 한다. 둘의 차이는
다루는 값 범위다 — `Lut Builder Ldr PS`는 LDR 범위(0~1)만, `Lut Builder Hdr PS`는 HDR 값
(1.0을 넘는 밝기)까지 다룬다.

## 요약

LUT PS 자체는 화면에 보이는 최종 이미지를 그리지 않는다 — 다음 단계(Uber PS)가 참조할 "색
변환 표"만 만들어서 작은 텍스처에 저장해두는, 일종의 사전 준비(precompute) 단계다. 이렇게
분리해두면 색 보정+톤 매핑이라는 무거운 수식을 화면 해상도만큼 반복하지 않고, 그 결과표를
프레임당 한 번만 계산하면 된다.

## 상세

### 왜 색 보정을 "표"로 만들 수 있는가 — 3D LUT의 원리

색 보정과 톤 매핑은 결국 "입력 RGB 색 하나를 받아서 출력 RGB 색 하나로 바꾸는 함수"다. 입력이
RGB 세 채널이니, 이 함수를 3차원 공간(R축·G축·B축)에서 "입력 좌표 → 출력 색" 매핑으로 생각할
수 있다. 모든 가능한 입력 색(수백만~수십억 가지 조합)에 대해 미리 계산해둘 수는 없지만, 각
축을 32단계로만 촘촘히 샘플링해도(32×32×32 = 32,768개 지점) 그 사이 값은 GPU의 텍스처
하드웨어가 **삼선형 보간(trilinear filtering)**으로 부드럽게 채워준다 — 그래서 32단계 정도의
LUT로도 눈에 띄는 계단 현상 없이 충분히 매끄러운 결과가 나온다.

### 무엇을 한 번에 굽는가

LutBuilderLdr/Hdr 셰이더는 다음 과정을 **LUT 텍스처를 만들 때 딱 한 번만** 순서대로 계산한다.

1. 화이트 밸런스(색 온도/색조 보정)
2. 노출, 대비(contrast)
3. 색조 곡선(커브), 채널 믹서, HSV 조정 같은 세부 색 보정
4. 채도(saturation)
5. **톤 매핑 곡선**(Neutral/ACES/커스텀) — [톤 매핑](../Graphics/Tone-Mapping.md) 참고

이 다섯 단계를 합친 "입력 색 → 출력 색" 함수 하나를 각 LUT 좌표(32×32×32개)에 대해 계산해서
텍스처 한 장에 채워 넣는다. 이후 `UberPost` 셰이더는 이 다섯 단계를 다시 계산하지 않고, 화면의
각 픽셀 색을 이 LUT 텍스처의 좌표로 변환해 **한 번 샘플링**하는 것만으로 다섯 단계를 전부 적용한
효과를 얻는다.

### LDR과 HDR 버전이 나뉘는 이유 — "무한한 값을 유한한 표에 담기"

여기서 실무적으로 까다로운 지점이 하나 있다. LUT의 좌표축은 반드시 유한한 범위(보통 0~1)여야
하는데, HDR 색상값은 1.0을 훌쩍 넘어 이론상 무한대까지 갈 수 있다. `LutBuilderHdr`는 이 문제를
**고정된 인코딩 함수**로 해결한다 — LUT를 구울 때, 실제 HDR 값을 그대로 좌표로 쓰지 않고
로그(log) 계열의 압축 함수를 한 번 거쳐서 "무한한 HDR 범위"를 "유한한 LUT 좌표 범위"로 접어
넣는다. 그리고 `UberPost`가 런타임에 실제 HDR 픽셀 값으로 LUT를 조회할 때도 **똑같은 인코딩
함수**를 적용해서 좌표를 구한다 — 굽는 쪽과 읽는 쪽이 같은 "자"를 쓰지 않으면 엉뚱한 색이
나오기 때문에, 이 인코딩 함수는 두 셰이더 사이에 반드시 짝이 맞아야 하는 암묵적 계약이다.
`LutBuilderLdr`는 이런 인코딩이 필요 없다 — 애초에 값의 범위가 0~1로 유한하기 때문에 좌표를
그대로 쓰면 된다.

### 성능 관점 — 왜 이 분리가 값어치를 하는가

풀HD(1920×1080) 기준 화면 픽셀 수는 약 200만 개다. 다섯 단계 색 보정 수식을 픽셀마다 매번
계산한다면 200만 번 반복해야 하지만, LUT로 구워두면 이 계산은 32,768번(32³)만 일어나고,
나머지 200만 픽셀은 훨씬 싼 텍스처 조회 한 번으로 끝난다 — 계산량이 대략 1/60 수준으로
줄어드는 셈이다. 게다가 카메라의 색 보정 설정(Volume)이 프레임마다 바뀌지 않는 한, 이 LUT는
매 프레임 다시 구울 필요조차 없어 추가로 캐싱할 여지도 있다.

## 비교표

| | `LutBuilderLdr` | `LutBuilderHdr` |
|---|---|---|
| 다루는 값 범위 | 0~1 (LDR) | 1.0을 넘는 HDR 값까지 |
| 좌표 인코딩 | 불필요(값 그대로 좌표) | 필요(로그 계열 인코딩으로 압축) |
| 쓰이는 상황 | HDR 디스플레이 출력이 아닌 일반 SDR 파이프라인 | HDR 디스플레이 출력, 또는 넓은 노출 범위를 다뤄야 하는 씬 |
| Uber PS와의 계약 | LUT 좌표 = 픽셀 색 그대로 | LUT 좌표 = 인코딩 함수(픽셀 색) — 양쪽이 같은 함수를 써야 함 |

## 질문

- **Q. LUT 해상도를 32보다 낮추거나 높이면 뭐가 달라지나?**
  A. 낮추면(예: 16×16×16) 텍스처 크기와 굽는 비용은 줄지만, 색이 급격히 변하는 구간(특히 강한
  커브나 채도 조정)에서 보간 오차로 인한 미세한 밴딩(계단 현상)이 보일 수 있다. 높이면(예:
  64×64×64) 정밀도는 좋아지지만 텍스처 용량이 8배로 늘고 굽는 비용도 커진다 — 32는 실무에서
  "육안으로는 거의 차이가 안 보이면서 비용은 합리적인" 절충점으로 널리 쓰인다.

- **Q. 톤 매핑 곡선을 커스텀하려면 왜 LUT PS를 건드려야 하나?**
  A. 톤 매핑 곡선 계산이 다섯 단계 중 마지막 단계로 LUT를 굽는 이 셰이더 안에 이미 포함돼 있기
  때문이다. `UberPost`는 이미 구워진 LUT를 샘플링만 할 뿐 톤 매핑 수식 자체를 모른다 — 그래서
  Neutral/ACES가 아닌 다른 곡선(예: GT 톤매퍼)을 쓰려면 LUT PS 안의 톤 매핑 계산 부분을 바꿔야
  하고, 그 결과가 그대로 LUT에 구워져서 Uber PS까지 자연스럽게 전달된다.

- **Q. LUT를 3D 텍스처가 아니라 2D 텍스처로 저장하는 경우도 있다던데?**
  A. 그렇다. GPU/API에 따라 3D 텍스처 샘플링 지원이 제한적이거나 비용이 더 클 때, 32×32×32
  3D LUT를 1024×32 크기의 2D 텍스처에 "펼쳐서" 저장하고(B축 32단계를 가로로 이어붙임),
  샘플링할 때 좌표 계산으로 이 펼침을 다시 풀어내는 방식을 쓰기도 한다 — 원리는 동일하고
  저장/샘플링 방식만 다르다.

## 예시 코드

```hlsl
// 개념을 보여주기 위한 최소 예시 — 실제 LutBuilderLdr 소스는 색 보정 단계가 훨씬 많다
float3 BuildLutEntry(float3 lutCoord)  // lutCoord: LUT 텍스처 상의 (r, g, b) 좌표, 0~1
{
    float3 color = lutCoord;               // 이 좌표 자체가 "입력 색"을 의미한다
    color = ApplyWhiteBalance(color);
    color = ApplyContrastAndCurves(color);
    color = ApplySaturation(color);
    color = ApplyTonemap(color);           // 톤 매핑 곡선 — Tone-Mapping.md 참고
    return color;                          // 이 값이 LUT 텍스처의 해당 좌표에 저장된다
}
```

```hlsl
// UberPost가 이 LUT를 실제로 쓰는 방식 — LDR 기준 최소 예시
float3 ApplyColorGradingLdr(float3 pixelColor, Texture3D lutTexture, SamplerState lutSampler)
{
    // pixelColor(0~1)를 그대로 좌표로 써서 삼선형 보간 샘플링 한 번
    return lutTexture.Sample(lutSampler, pixelColor).rgb;
}
```

`Tone-Mapping.flow.md`의 `BAKE`/`SAMPLE` 단계가 정확히 이 문서의 LUT PS/Uber PS 관계를
나타낸다 — 별도 플로우차트 없이 그 그림으로 충분하다.

## 실무

실무에서는 이 "미리 굽고 나중에 조회한다"는 패턴이 색 보정에만 쓰이지 않는다 — 서브서피스
스캐터링 근사, 대기 산란(atmospheric scattering), 심지어 일부 BRDF 근사도 비슷하게 LUT로
구워서 런타임 비용을 텍스처 조회 수준으로 낮추는 경우가 흔하다. "함수를 매 픽셀 계산할지, 미리
표로 만들어둘지"는 그래픽스 최적화에서 반복적으로 등장하는 선택지이고, LUT PS는 그 전형적인
예시를 아주 잘 보여주는 사례다. 영화/사진 편집 도구(DaVinci Resolve, Photoshop 등)에서 흔히
쓰는 `.cube` LUT 파일도 원리는 완전히 동일하다 — 색보정 소프트웨어에서 만든 LUT를 그대로
게임 엔진에 가져와 적용하는 워크플로우도 실무에서 널리 쓰인다.
