## 정의

톤 매핑은 렌더러가 물리적으로 계산해낸 **HDR(High Dynamic Range) 색상값**(밝기가 0~1 범위를
훌쩍 넘어 태양광이면 수백~수천 배까지 올라갈 수 있는 값)을, 모니터가 실제로 표시할 수 있는
**LDR(Low Dynamic Range) 범위**(보통 0~1, 8비트 채널 기준 0~255)로 압축해서 옮겨 담는 과정이다.
단순히 값을 잘라내는(clamp) 게 아니라, 밝은 영역의 디테일(하이라이트 롤오프)과 어두운 영역의
디테일(섀도우)을 최대한 자연스럽게 유지하면서 압축하는 게 핵심이다.

## 요약

톤 매핑은 "HDR 렌더링 결과 → 화면에 보여줄 최종 색"으로 가는 마지막 관문이고, 이 변환에 어떤
곡선(커브)을 쓰느냐에 따라 같은 씬도 전혀 다른 그림이 된다 — Unity URP는 기본으로 Neutral과
ACES 두 가지를 제공하지만, 실무에서는 프로젝트의 비주얼 방향에 맞춰 곡선 자체를 바꿔치기하는
경우가 흔하다.

## 상세

### 왜 그냥 clamp(0, 1)로 끝내면 안 되는가

HDR 렌더링 파이프라인에서 픽셀 셰이더가 계산해낸 최종 색은 물리 단위(예: 조도)를 그대로 반영하기
때문에 1.0을 아득히 넘는 값이 흔하다. 이 값을 그냥 `clamp(color, 0, 1)`로 잘라버리면, 1.0을
넘는 모든 값이 전부 순백색(1,1,1)으로 뭉개진다 — 태양 주변도, 형광등 갓도, 살짝 과노출된
피부도 전부 같은 흰색이 되어 디테일이 통째로 사라진다. 이걸 **hard clipping**이라 부르고, 톤
매핑이 풀어야 하는 문제가 정확히 이것이다: "1.0을 넘는 값들 사이에도 상대적인 밝기 차이가
있다는 정보를 최대한 살리면서 0~1 안으로 눌러 담는다."

### 곡선의 공통된 모양 — S자 커브

대부분의 실용적인 톤 매핑 곡선은 그래프로 그리면 완만한 **S자**를 그린다.

- **토(toe, 어두운 영역)**: 살짝 아래로 눌러서 검은색이 너무 붕 뜨지 않게(블랙 레벨을 조인다).
- **선형 구간(중간 톤)**: 원본 대비를 거의 그대로 유지 — 사람 눈이 가장 민감한 구간이라 왜곡을
  최소화한다.
- **숄더(shoulder, 밝은 영역)**: 위로 갈수록 완만하게 눌러서(롤오프) 1.0에 무한히 가까워지되
  절대 값이 튀지 않게 한다 — 이 부분이 hard clipping 없이 하이라이트 디테일을 살리는 핵심이다.

이 S자 모양 자체가 필름 카메라의 감광 특성(필름이 빛에 반응하는 비선형 곡선)을 흉내 낸 것이라
"필름(filmic)" 톤 매핑이라는 이름이 붙기도 한다 — 실제 필름이 하이라이트를 부드럽게 뭉개면서도
디테일을 남기는 방식을 디지털로 재현한 셈이다.

### Unity URP의 실무 적용 지점

URP의 Volume 프로파일에서 "Tonemapping" 오버라이드를 켜면 `None`/`Neutral`/`ACES` 세 가지 모드
중 고를 수 있다. 이 계산이 실제로 일어나는 곳은 크게 두 갈래다.

1. **LDR 그레이딩 경로**: `LutBuilderLdr` 셰이더가 색 보정(화이트 밸런스, 커브, 채널 믹서 등)과
   톤 매핑 곡선을 한 번에 계산해서 작은 3D LUT(Look-Up Table) 텍스처 하나에 구워 넣고,
   `UberPost` 셰이더가 화면 전체 픽셀마다 이 LUT를 한 번씩 샘플링해서 최종 색을 얻는다 — 자세한
   원리는 [LUT PS](./LUT-PS.md) 참고.
2. **HDR 출력 경로**(디스플레이 자체가 HDR을 지원하는 경우): `LutBuilderHdr`가 대신 쓰이며, LUT의
   유효 범위를 HDR 값까지 확장해서 굽는다.

실무에서 톤 매핑 자체를 커스텀하고 싶을 때(예: 아래에서 다룰 GT 톤매퍼 도입) 이 두 셰이더가
바로 손대야 할 지점이 된다 — Unity가 Volume 오버라이드로 노출한 `None`/`Neutral`/`ACES` 세
선택지 바깥의 곡선을 쓰려면, URP 소스 자체를 고치거나(유지보수 부담이 큼) 이 셰이더들을
`Post Process Data` 에셋에서 커스텀 버전으로 **교체**해야 한다. Post Process Data 에셋(URP
렌더러 세팅에서 참조)에는 이런 내부 셰이더들의 레퍼런스가 그대로 노출돼 있어서, 이 레퍼런스만
바꿔치기하면 스크립터블 렌더 패스를 새로 추가하는 것보다 훨씬 적은 부작용으로 원하는 톤 매핑
알고리즘을 끼워 넣을 수 있다 — 패스 순서나 중복 실행 문제를 새로 만들지 않기 때문이다.

## 비교표 — 대표적인 톤 매핑 곡선

| 곡선 | 핵심 아이디어 | 특징 | 실무에서 어울리는 상황 |
|---|---|---|---|
| Reinhard `x/(1+x)` | 가장 단순한 압축 공식 하나로 전체 범위를 눌러 담는다 | 계산이 매우 싸지만 하이라이트가 갈수록 뿌옇게 채도가 빠지고(desaturate), 대비가 밋밋해지는 경향이 있다 | 프로토타입, 성능이 극도로 중요한 초저사양 타겟 |
| ACES (Unity 근사식) | 영화 산업 표준 색 관리 체계(ACES)의 필름 룩을 그대로 재현하도록 수학적으로 근사한 곡선 | 대비와 채도가 강하게 살아 "시네마틱"하지만, 원본 색상을 상당히 왜곡시킨다는 단점도 있다 | 사실적 톤의 3D 게임, PBR 기반 리얼리즘 프로젝트 |
| Neutral (Unity 기본) | ACES보다 원본 색을 덜 왜곡하는 걸 목표로 한 절충안 | 대비가 ACES보다 약해 "밋밋하다"는 인상을 줄 수 있지만, 아트가 이미 잡아둔 색을 그대로 보여주고 싶을 때 유리 | 스타일라이즈드 아트, 색상 정확도가 중요한 UI/캐주얼 게임 |
| GT 톤매퍼(Uchimura, CEDEC 2017) | 토/선형/숄더 세 구간의 길이·기울기·검정 레벨을 파라미터로 직접 조절할 수 있는 범용 곡선 | 파라미터가 많아 튜닝 자유도가 가장 높다 — 대신 아티스트가 직접 맞춰야 할 값도 많다 | 프로젝트마다 원하는 룩이 뚜렷이 다른 스타일라이즈 프로젝트(영상 속 발표자가 "개인적으로 자주 쓴다"고 언급한 이유) |
| AgX / Filmic(Hable, Uncharted 2) | GT 톤매퍼와 비슷한 계열의 필름 감성 커브, 각기 다른 튜닝 철학 | URP 기본 제공 목록엔 없어 커스텀 셰이더로만 적용 가능 | 참고용 — 최신 트렌드(특히 AgX)를 따라가고 싶을 때 |

**표를 읽는 법**: 왼쪽일수록 "계산은 싸지만 결과가 거칠다", 오른쪽일수록 "결과는 좋지만 파라미터를
사람이 튜닝해야 한다"는 트레이드오프가 대략적으로 성립한다. 정답은 없고, 프로젝트의 아트 방향과
타겟 하드웨어 성능이 선택을 가른다.

## 질문

- **Q. ACES와 Neutral 중 뭘 기본값으로 써야 하나?**
  A. 정답은 없지만 기준은 있다 — 아트팀이 색을 매우 정교하게 맞춰둔 프로젝트(예: 캐주얼/스타일라이즈)라면
  Neutral이 그 색을 덜 망가뜨린다. 반대로 사실적인 조명/재질을 강조하고 싶다면 ACES의 강한 대비가
  "영화 같은" 인상을 준다. 둘 다 URP에 내장돼 있어 전환 비용이 없으니, 실제로 씬에 놓고 눈으로
  비교하는 게 가장 빠르다.

- **Q. 톤 매핑 곡선을 바꾸면 왜 게임 전체의 색이 다 달라 보이나?**
  A. 톤 매핑은 색 보정(화이트 밸런스, 노출, 채도 등) **이후**, 화면에 찍기 **직전** 마지막 단계에서
  전체 프레임에 균일하게 적용되기 때문이다. 개별 오브젝트의 머티리얼을 하나도 안 건드려도, 이
  마지막 곡선 하나만 바꾸면 게임의 전체 인상(콘트라스트, 채도, "필름 느낌")이 통째로 바뀐다 —
  포스트 프로세싱이 "값싸게 전체 룩을 바꾸는 지렛대"로 취급되는 이유다.

- **Q. 톤 매핑을 아예 끄면(`None`) 무슨 일이 생기나?**
  A. HDR 색이 그대로 clamp만 되어 화면에 나간다. 노출이 정확히 맞춰진 장면이 아니라면 하이라이트가
  바로 순백색으로 날아가는 hard clipping이 눈에 띄게 보인다 — 디버깅 목적(원본 HDR 값을 그대로
  확인하고 싶을 때)이 아니면 실제 출시 빌드에서 끄는 경우는 드물다.

## 예시 코드

```hlsl
// Reinhard — 가장 단순한 톤 매핑, 원리를 보여주기 위한 최소 예시
float3 ReinhardTonemap(float3 hdrColor)
{
    return hdrColor / (1.0 + hdrColor);
}
```

```hlsl
// ACES 근사식(Krzysztof Narkowicz 피팅, 공개적으로 널리 쓰이는 버전) —
// Unity가 내부적으로 쓰는 정확한 계수와는 다를 수 있으나 곡선의 성질은 동일하다
float3 ACESFilmApprox(float3 x)
{
    const float a = 2.51, b = 0.03, c = 2.43, d = 0.59, e = 0.14;
    return saturate((x * (a * x + b)) / (x * (c * x + d) + e));
}
```

## 실무

실무에서는 "어떤 곡선을 쓰느냐"보다 "그 곡선을 얼마나 싸게 적용하느냐"가 더 큰 엔지니어링
과제인 경우가 많다. Unity URP를 포함해 대부분의 실시간 렌더러는 톤 매핑 수식을 픽셀마다 직접
계산하지 않고, 작은 3D LUT 텍스처에 미리 구워 넣은 뒤 그 LUT를 샘플링하는 방식을 쓴다 —
[LUT PS](./LUT-PS.md)에서 이 방식 자체를 다룬다. 최근 업계 동향으로는 Blender/Unreal이 채택하며
주목받은 **AgX** 톤매퍼가 "고채도 색이 뭉개지지 않는다"는 평가를 받으며 확산 중이고, Unity
진영에서도 커스텀 셰이더로 이식하는 사례가 늘고 있다.
