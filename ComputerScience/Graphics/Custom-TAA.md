## 정의

TAA(Temporal Anti-Aliasing)는 프레임마다 카메라를 미세하게 흔들면서(지터, jitter) 컬러 버퍼를
누적해, 여러 프레임에 걸쳐 서브픽셀 정보를 채워 넣는 안티에일리어싱 기법이다. 한 프레임만 보면
평범한 해상도지만, 여러 프레임이 누적되면 마치 훨씬 고해상도로 렌더링한 것 같은 효과를 낸다 —
DLSS나 FSR 같은 업스케일링 솔루션도 근본적으로 같은 "시간축 누적" 원리 위에 서 있다.

## 요약

TAA는 렌더 해상도를 낮춰도 화질을 상당 부분 보완해주기 때문에 모바일 대역폭 절감에 특히
유용하지만, URP 내장 TAA는 품질을 충분히 올려야 고스팅/블러 아티팩트가 잡히고 그러면 다시
무거워지는 딜레마가 있었다. 발표자는 **히스토리 리젝션**, **모션 블렌드 팩터**,
**단순화된 컬러 클램핑** 세 가지 전략으로 이 딜레마를 URP 패키지 자체를 고치지 않고
풀어냈다.

## 상세

### 왜 렌더 스케일을 낮추고 TAA로 보완하나

모바일 게임이 SSAO, 스크린 스페이스 섀도우, 블룸, DOF 같은 풀스크린 효과를 늘려갈수록 메모리
대역폭 압박이 커진다. 발표자는 이 압박을 줄이는 방법으로 **렌더 스케일 자체를 낮추고(예:
0.6배) 그 화질 손실을 TAA로 보완**하는 접근을 택했다. 실제로 URP 샘플 프로젝트(판타지 킹덤)
기준 렌더 스케일 1.0 + 안티에일리어싱 없음과, 렌더 스케일 0.6 + 커스텀 TAA를 비교했을 때 GPU
타임 30%, 메모리 대역폭 20% 개선이 있었다고 한다.

### URP 내장 TAA를 그대로 못 쓴 이유

TAA의 대표적인 아티팩트는 **고스팅**(움직이는 물체 뒤에 잔상이 남는 현상)과 **블러**(전체적으로
살짝 뭉개지는 현상)다. URP 내장 TAA는 이 아티팩트를 억누르려면 품질 옵션을 상당히 높여야
했는데, 그러면 앞서 렌더 스케일을 낮춰 확보한 대역폭 이득이 도로 상쇄됐다 — "품질 낮추면
아티팩트, 품질 높이면 무거움"의 반복이 발표자가 커스텀을 결심한 계기였다.

### 전략 1 — 히스토리 리젝션(History Rejection)

TAA는 "이전 프레임 정보(히스토리)를 지금 픽셀에 얼마나 섞을지"가 핵심인데, 애초에 신뢰할 수
없는 히스토리를 가진 픽셀에는 아예 TAA를 적용하지 않는 게 히스토리 리젝션의 개념이다. 이를
위해 **모션 마스크**라는 텍스처를 모션 벡터 패스에서 멀티 렌더 타겟으로 함께 그리는데, 여기엔
두 가지 값이 기록된다.

- 스킨/트랜스폼이 바뀌는 오브젝트: `0.5`
- 파티클, UV 스크롤처럼 애초에 모션 벡터 정보가 없는 대상: `1.0`

TAA 패스에서는 이전 프레임과 현재 프레임의 모션 마스크를 함께 샘플링해 두 종류의 "리젝션 대상"
픽셀을 판정한다.

1. **모션 벡터가 아예 없는 픽셀**(파티클, UV 스크롤 등) — 발표 시각화에서 파란색으로 표시.
2. **디스오클루전(disocclusion) 픽셀** — 이전 프레임엔 가려져 안 보이다가 이번 프레임에 새로
   드러난 픽셀(빨간색). 애초에 누적된 히스토리 자체가 없으므로 TAA를 적용하면 오히려 블러가
   생긴다.

두 경우 모두 히스토리를 신뢰할 수 없다고 판단해 TAA를 아예 건너뛴다 — "잘못된 정보를 섞느니
안 섞는다"는 방어적인 선택이다.

### 전략 2 — 모션 블렌드 팩터(Motion Blend Factor)

모션 벡터의 크기로 "이 픽셀이 얼마나 빠르게 움직였는가"를 판정해서, 많이 움직인 픽셀일수록
히스토리 반영 비율을 낮추고(고스팅 억제), 정적인 픽셀일수록 반영 비율을 높인다(화질 개선
극대화). 히스토리 리젝션이 "아예 켜거나 끄거나"의 이진 판정이라면, 모션 블렌드 팩터는 그
사이를 연속적으로 조절하는 역할을 한다.

### 전략 3 — 컬러 클램핑 단순화 + 스페큘러 안티에일리어싱

앞선 두 전략으로 조건부 처리가 이미 상당히 들어간 상태라, TAA 내부에서 가장 무거운 연산인
**컬러 클램핑**(히스토리 색이 현재 프레임의 주변 픽셀 색 범위를 벗어나지 않게 눌러주는 과정,
고스팅 억제에 쓰임)을 URP TAA의 "Very Low" 품질 단계와 동일한 가장 단순한 알고리즘으로
고정했다. 문제는 이 단순한 클램핑만으로는 미세한 스페큘러 하이라이트가 카메라 지터 때문에
깜빡이는(flickering) 현상을 못 잡아준다는 것 — 원래는 더 높은 수준의 클램핑 알고리즘이 이걸
보완하지만, 발표자는 이 보완을 TAA 쪽에서 하지 않고 **머티리얼 셰이더 안에서 스페큘러
안티에일리어싱 기법**을 적용해 해결했다. "TAA 하나가 모든 걸 해결하게 만들지 않고, 문제의
원인에 가까운 곳(셰이더)에서 미리 잡는다"는 접근이다.

### 부가 — 셔프닝을 TAA 패스 안으로 통합

TAA는 원리상 여러 프레임을 섞는 과정에서 이미지가 살짝 뭉개지는 경향이 있어 보통 후처리로
샤프닝을 적용한다. URP 내장 TAA는 이 샤프닝을 TAA 패스 이후 별도의 파이널 포스트 패스에서
수행하는데, 발표자는 이걸 **TAA 패스 내부로 통합**했다 — 컬러 클램핑 과정에서 이미 주변 픽셀을
샘플링하고 있으므로, 샤프닝에 필요한 주변 픽셀 정보를 다시 조회할 필요 없이 같은 샘플링 결과를
재사용할 수 있어 효율적이라는 판단이었다.

### 대역폭 최적화 — 모션 벡터 텍스처 압축과 메모리리스 스텐실

TAA는 참조하는 렌더 텍스처와 샘플러가 많아 대역폭 부담이 큰 피처인 데다, 커스텀 TAA는 모션
마스크 텍스처 두 개(이전/현재 프레임)까지 추가로 샘플링한다. 발표자는 이를 상쇄하기 위해 다음을
적용했다.

- **모션 벡터 포맷 압축**: 기본 `RG16` 포맷을 `RG8`로 줄이면서, 단순 선형 압축이 아니라
  **제곱근(sqrt) 기반 비선형 인코딩**으로 정밀도를 보정했다. TAA에서 블러리함이 두드러지는
  경우가 주로 "픽셀이 느리고 미세하게 움직일 때"이므로, 값이 작은 구간(느린 움직임)에 더 많은
  비트를 배정하는 비선형 인코딩으로 그 구간의 정밀도를 끌어올렸다.
- **모션 벡터 스텐실 버퍼를 메모리리스(memoryless)로**: 모션 벡터 패스 내부에서만 쓰이고
  이후엔 재사용되지 않는 자체 스텐실 버퍼를, 렌더그래프의 Raster API로 시스템 메모리에 아예
  저장되지 않도록(타일 메모리에서만 쓰이고 버려지도록) 설정했다. 다만 이 메모리리스 동작은
  발표 시점 기준 메탈(iOS) API에 한정된 것으로 확인됐고, Vulkan/OpenGL에서는 다르게 동작할 수
  있다고 발표자가 직접 언급했다 — 메모리 용량 절감은 확실하지만 타일 메모리 동작까지는
  검증하지 못했다는 단서를 남겼다.
- **TAA 카피 패스 조건부 생략**: TAA 결과를 다음 프레임에 넘기기 위한 카피 패스가 있는데, TAA
  패스 이후 컬러 버퍼가 더 이상 수정되지 않고 그대로 백버퍼에 그려지는 상황이라면 이 카피
  자체가 불필요하다. 컬러 버퍼가 이후 단계에서 실제로 수정되는지를 감지해서, 필요한 상황에서만
  카피 패스를 실행하도록 만들었다 — 렌더 텍스처 하나에 대한 카피 자체가 통째로 사라지는 경우가
  많아 대부분의 상황에서 최적화 효과가 컸다고 한다.

### URP 패키지를 고치지 않고 내장 TAA를 끄는 방법

발표에서 가장 실용적인 부분은 "카메라 컴포넌트에서 TAA 옵션 하나만 켜도 URP 내장 경로 내부에서
수많은 처리가 함께 일어나기 때문에, 특정 셰이더나 패스 하나만 갈아 끼우는 방식으로는 대체할 수
없었다"는 문제를 어떻게 풀었느냐다. 전략은 세 가지다.

1. **지터 행렬(jitter matrix)은 URP 내장 경로를 그대로 유지**한다 — 카메라의 프로젝션 행렬은
   TAA뿐 아니라 다른 렌더 패스에서도 일관되게 참조되므로, TAA만을 위해 이 값을 따로 건드리면
   다른 곳에 사이드 이펙트가 생긴다.
2. **내장 TAA와 내장 모션 벡터 패스만 비활성화**한다 — 커스텀 렌더 패스에서 `BeforeRendering`
   같은 이른 시점에 카메라 데이터의 TAA 옵션을 꺼버리고, URP 내장 카메라 모션 벡터 머티리얼을
   삭제한다. 이게 가능한 이유는, 스크립터블 렌더 패스가 참조하는 카메라 데이터가 씬의 카메라
   컴포넌트 원본이 아니라 **그 프레임의 렌더 패스용으로 복제된 데이터**이기 때문이다 — 여기서
   값을 바꿔도 씬의 카메라 컴포넌트 자체는 영향받지 않고, 그 프레임의 렌더 패스 실행에만
   영향을 준다. 모션 벡터 머티리얼은 내부 코드가 "머티리얼이 null이면 그대로 리턴"하도록
   짜여 있다는 걸 발견해서, 어셈블리 리플렉션으로 그 머티리얼을 강제로 지우는 방식으로 우회했다.
3. **비활성화된 자리에 커스텀 렌더 피처를 새로 추가**해서, 커스텀 TAA와 커스텀 모션 벡터
   패스를 대신 호출하도록 만든다.

발표자 스스로도 "이게 안전한 방법인가?"라는 질문을 던졌는데, 적어도 Unity 2022~6.0 범위에서는
동작을 확인했고, 이후 버전에서 막히면 새 우회 방법을 찾거나 최악의 경우 URP 패키지를 직접
수정하는 방향으로 갈 것이라고 밝혔다. 여러 프로젝트를 동시에 지원해야 하는 조직 구조라
유지보수 비용 때문에 패키지 비수정 방식을 택했을 뿐, 단일 프로젝트만 지원한다면 오히려 URP
패키지를 직접 수정하는 쪽이 더 효율적일 수 있다고 스스로 단서를 달았다.

## 비교표

| 항목 | URP 내장 TAA | 커스텀 TAA |
|---|---|---|
| 고스팅/블러 억제 | 품질 옵션을 높여야 억제됨(그만큼 무거워짐) | 히스토리 리젝션 + 모션 블렌드로 낮은 연산량에서도 억제 |
| 컬러 클램핑 | 품질별로 여러 단계 알고리즘 | Very Low 수준으로 고정, 대신 스페큘러 안티에일리어싱을 셰이더에서 별도 처리 |
| 샤프닝 위치 | 별도의 파이널 포스트 패스 | TAA 패스 내부(주변 픽셀 샘플링 재사용) |
| 모션 벡터 포맷 | RG16 | RG8 + 비선형(sqrt) 인코딩 |
| 도입 방식 | 기본 제공 | URP 패키지 수정 없이 리플렉션 + 커스텀 렌더 피처로 대체 |
| 실측(전체 프레임 기준) | 기준값 | GPU 타임 21%↓, 메모리 대역폭 17%↓ |

## 질문

- **Q. 히스토리 리젝션과 모션 블렌드 팩터는 서로 뭐가 다른가?**
  A. 히스토리 리젝션은 "이 픽셀에 TAA를 적용할지 말지"를 결정하는 이진 판정(신뢰할 수 없는
  히스토리는 아예 배제)이고, 모션 블렌드 팩터는 "TAA를 적용하되 히스토리를 얼마나 강하게
  반영할지"를 연속적으로 조절하는 값이다. 전자가 "극단적으로 문제가 되는 픽셀을 걸러내는
  안전장치"라면, 후자는 "걸러지지 않은 나머지 픽셀들 사이에서 품질과 아티팩트의 균형을 맞추는
  다이얼"에 가깝다.

- **Q. 렌더 패스가 참조하는 카메라 데이터가 "복제본"이라는 게 왜 이 우회의 핵심인가?**
  A. 만약 렌더 패스가 씬의 카메라 컴포넌트 원본을 직접 참조했다면, TAA 옵션을 끄는 순간 씬의
  카메라 설정 자체가 영구적으로 바뀌어버려 다른 시스템(에디터 UI, 다른 스크립트)에서 예상치
  못한 부작용이 생겼을 것이다. 프레임마다 새로 복제되는 데이터이기 때문에, 그 프레임의 렌더링
  경로만 조용히 바꿔치기하고 다음 프레임엔 다시 원래 상태에서 복제가 시작된다 — 원본을 건드리지
  않고 "이번 프레임만" 다르게 동작시키는 전형적인 패턴이다.

- **Q. 메모리리스 렌더 타겟은 왜 API마다 동작이 다를 수 있나?**
  A. "메모리리스"는 타일 기반 GPU 아키텍처(모바일 GPU 대부분)가 렌더 타겟을 시스템 메모리에
  내려쓰지 않고 온칩 타일 메모리에서만 쓰고 버릴 수 있게 해주는 최적화인데, 이걸 그래픽스
  API/드라이버가 얼마나 잘 지원하고 활용하느냐는 벤더·API마다 다르다. 발표자가 메탈(iOS)
  기준으로만 검증하고 Vulkan/OpenGL은 다를 수 있다고 명시한 것도 이런 플랫폼 종속성 때문이다.

## 예시 코드

```hlsl
// 개념을 보여주는 최소 예시 — 모션 마스크 기반 히스토리 리젝션 판정
float ComputeHistoryWeight(float prevMask, float currMask, float2 motionMagnitude)
{
    // 모션 벡터 자체가 없는 픽셀(마스크 1.0 근방) → 히스토리 완전 배제
    if (currMask > 0.9) return 0.0;

    // 디스오클루전: 이전 프레임 마스크와 현재 프레임 마스크가 크게 어긋나면
    // "이전엔 안 보이던 픽셀"로 판단해 히스토리 배제
    if (abs(prevMask - currMask) > DISOCCLUSION_THRESHOLD) return 0.0;

    // 그 외엔 움직임 크기에 따라 연속적으로 블렌드 비율을 낮춘다(모션 블렌드 팩터)
    return saturate(1.0 - length(motionMagnitude) * MOTION_BLEND_SCALE);
}
```

## 실무

실무에서 TAA는 이제 거의 모든 실시간 3D 게임의 기본 안티에일리어싱으로 자리잡았고, DLSS/FSR
같은 업스케일링 기술의 기반이기도 하다 — TAA의 핵심 메커니즘(지터, 히스토리 누적, 리젝션,
컬러 클램핑)을 이해하면 이런 최신 업스케일러들의 동작 원리도 훨씬 쉽게 이해된다. 다만 이
사례처럼 "엔진 내장 기능을 패키지 수정 없이 리플렉션으로 우회해 대체"하는 접근은 안정성
트레이드오프가 있다 — 엔진 버전이 올라갈 때마다 내부 구현이 바뀌어 우회 코드가 깨질 위험을
안고 가는 대신, 여러 프로젝트에 배포된 패키지를 개별적으로 패치·유지보수해야 하는 부담을
피하는 선택이다. 조직이 몇 개의 프로젝트를 얼마나 오래 지원해야 하는지에 따라 이 트레이드오프의
답이 달라진다.
