## 출처

`RottenNoble-Project`의 홈 화면에 배경 연출을 넣기로 하면서(원래는 티스토리 글 이관 작업을
하려다 "디자인부터 정하자"고 멈춘 김에 나온 아이디어), 이미지 에셋 없이 GLSL 코드만으로 다크
톤 배경에 은은한 빛과 별을 띄우는 셰이더를 실제로 짜고, 사용자의 라이브 피드백을 받아가며
색감·속도·블러 체감을 여러 차례 튜닝한 과정을 정리한다.

## 정의

절차적 셰이더(procedural shader)는 텍스처 이미지 같은 미리 만들어둔 자산을 읽는 대신, 매
픽셀의 색을 수학 함수로 그 자리에서 계산해서 그리는 방식이다. 이 문서가 다루는 배경은 그 중에서도
**value noise**(격자점마다 무작위 값을 정해두고 그 사이를 부드럽게 보간하는 노이즈)와, 그 노이즈를
여러 겹 쌓아 자연스러운 얼룩을 만드는 **fBm**(fractal Brownian motion, 프랙탈 브라운 운동)을
핵심 재료로 쓴다.

## 요약

hash 함수로 결정론적 의사난수를 만들고, 그 위에 격자 보간(value noise)을 얹고, 그 노이즈를
주파수/진폭을 바꿔가며 2단계 겹쳐 쌓는 fBm으로 부드러운 성운 구름을 그렸다. 별은 같은 격자를
훨씬 촘촘하게 나눈 뒤 셀 하나당 무작위로 흔든 점 하나만 찍는 방식(Worley/Voronoi 스타일 단일점
샘플링)으로 표현했다. 텍스처 자산은 하나도 안 쓰고, 옥타브 수와 GLSL `precision`을 낮춰 저사양
GPU에서도 매 프레임 가볍게 계산되도록 맞췄다.

## 상세

### hash와 value noise — 난수 대신 결정론적 의사난수

셰이더는 매 프레임 병렬로 계산되기 때문에, 일반 프로그래밍 언어의 "상태를 가진 난수 생성기"를
쓸 수 없다. 대신 **입력이 같으면 항상 같은 값이 나오는 결정론적 해시 함수**를 쓴다. 이 프로젝트의
`hash(vec2 p)`는 좌표를 몇 번 곱하고 더한 뒤 소수점 아래만 남기는(`fract`) 방식으로, 겉보기엔
무작위처럼 보이지만 같은 좌표를 넣으면 항상 같은 값이 나오는 함수다.

이 hash만으로는 격자점마다 뚝뚝 끊기는 값만 나온다. 격자 네 꼭짓점의 hash 값을 부드러운 곡선
(`smoothstep` 계열의 3차 보간, `f*f*(3-2*f)`)으로 섞으면, 격자 사이사이가 매끄럽게 이어지는
**value noise**가 된다 — 이게 구름처럼 보이는 얼룩의 최소 단위다.

### fBm — 옥타브를 쌓아 자연스러운 얼룩 만들기

value noise 하나만 쓰면 얼룩이 너무 단조롭고 규칙적으로 보인다. fBm은 이 노이즈를 주파수를
점점 높이고 진폭을 점점 낮추면서 여러 번(옥타브) 겹쳐 더한다 — 큰 옥타브는 전체적인 큰 덩어리를,
작은 옥타브는 그 위에 얹히는 잔잔한 디테일을 담당한다. 실제 코드는 옥타브 2개짜리로 짧게 짰다:

```glsl
float fbm(vec2 p) {
  float v = 0.0;
  float amp = 0.6;
  float freq = 1.0;
  for (int i = 0; i < 2; i++) {
    v += amp * noise(p * freq);
    freq *= 2.15;
    amp *= 0.55;
  }
  return v;
}
```

옥타브가 5개, 6개로 늘어날수록 디테일은 풍부해지지만 픽셀당 `noise()` 호출(그 안에 `hash()`가
4번씩 들어있다)이 그만큼 늘어 GPU 비용이 커진다. 이 프로젝트는 배경일 뿐 시선을 끄는 주인공이
아니므로, 2옥타브로도 충분히 "구름 같은 얼룩"이라는 목적은 달성된다고 판단했다.

### 별을 찍는 두 가지 방법 — 격자 정중앙 vs Worley 스타일 지터링

처음 버전은 화면을 촘촘한 격자로 나누고, 각 칸의 hash 값이 어떤 임계값을 넘으면 그 칸의
**정중앙**에 별 하나를 찍는 방식이었다. 이러면 별이 존재할지 말지는 무작위지만, 존재하는
별들의 위치는 전부 격자에 딱 맞춰 정렬돼 있어서 자세히 보면 인위적인 격자 패턴이 눈에 띈다.

이를 "셀 하나당 점 하나, 단 그 점의 위치도 셀 안에서 무작위로 흔든다"는 방식으로 바꿨다 —
그래픽스에서 흔히 Worley noise(또는 Voronoi 노이즈의 한 형태로 다뤄지는 "셀당 1점" 샘플링)라고
부르는 기법과 같은 아이디어다.

```glsl
vec2 gi = floor(starGrid);
vec2 gf = fract(starGrid) - 0.5;
vec2 jitter = vec2(hash(gi + 0.17), hash(gi + 5.31)) - 0.5;
float starHash = hash(gi + 11.7);
float starMask = step(0.9965, starHash);
float starDist = length(gf - jitter * 0.8);
```

`jitter`가 셀 중심에서 얼마나, 어느 방향으로 벗어날지를 정하고, 별의 밝기(`star`)는 그 흔들린
점까지의 거리로 계산한다. 존재 여부(`starHash`)와 흔들림(`jitter`)을 서로 다른 hash 시드로
분리해둔 것도 중요한데, 같은 값을 재사용하면 "별이 있는 칸일수록 특정 방향으로만 치우쳐 흔들리는"
식의 상관관계가 생겨 오히려 규칙적으로 보일 수 있기 때문이다.

### 드리프트 — 시간에 따른 이동으로 정적인 그림에 생명 불어넣기

정지된 fBm 얼룩은 그냥 얼룩덜룩한 벽지처럼 보인다. 시간(`u_time`)에 비례하는 오프셋을 노이즈
입력 좌표에 더해서 샘플링 위치 자체를 매 프레임 이동시키면, 화면은 고정된 채 그 아래 무늬가
흘러가는 것처럼 보인다.

```glsl
vec2 drift = u_time * vec2(0.15, 0.095);
float n = fbm(p * 2.2 + drift);
```

처음엔 두 축에 같은 계수(`u_time * 0.01`)를 더했는데, 이론상으로는 이미 대각선(45도) 방향
이동이었지만 계수가 너무 작아 사용자에게는 거의 정지한 것처럼 보였다. `x`/`y` 계수를 다르게
주고 크기를 3배 가까이 키우자("성운 속도가 더 빨랐으면 좋겠다"는 피드백) 비로소 "구름이 대각선
으로 흘러간다"는 느낌이 확실히 드러났다 — 벡터의 방향이 옳아도 크기가 지각 임계값 아래면
사실상 "안 움직이는 것"과 같다는 걸 보여주는 사례다.

### GPU 비용 다이얼 — 옥타브 수, precision, 루프 여부

같은 셰이더를 두 번 다시 짜면서 조정한 비용 관련 선택지:

- **옥타브 수**: 5개(회전 행렬까지 곁들인 버전) → 2개로 축소. `noise()` 호출 횟수(= `hash()`
  호출 횟수)가 옥타브 수에 정비례하므로 가장 직접적인 비용 손잡이다.
- **precision**: `precision highp float` → `precision mediump float`. 모바일 GPU는
  `mediump`가 훨씬 저렴하고, 배경 연출처럼 미세한 정밀도 차이가 안 보이는 용도엔 `mediump`로도
  충분하다.
- **루프 vs 언롤링**: 처음엔 "루프 없이 `noise()`를 두 번 직접 호출"하는 형태로 짰다가,
  사용자가 "루프는 넣어줘!!"라고 명시적으로 요청해서 `for (int i = 0; i < 2; i++)` 루프로
  되돌렸다. 실행 비용 자체는 동일하다(옥타브 수가 컴파일 타임 상수라 GLSL 컴파일러가 대부분
  언롤링한다) — 이 요청은 성능 문제가 아니라 **코드를 나중에 옥타브를 늘리기 쉽게 유지보수하고
  싶다**는 의도였다.

### 실제 튜닝 과정 — 라이브 배포 후 피드백으로 색감/블러 체감 조정

이 배경은 로컬에 노드가 없던 세션에서 처음 만들어져 `develop` 머지(=라이브 배포) 후에야
실제로 어떻게 보이는지 확인할 수 있었다(관련: 스테이징 환경 부재 문제, [Playwright 로컬
검증](../WebDevelopment/Playwright-Local-Verification.md) 참고). 배포 후 사용자 피드백은
이랬다:

> "보라색이라 그런지 블러가 약하게 먹히거든... 파스텔 푸른색이였으면 좋겠어. 성운 속도가 좀 더
> 빨랐으면 좋겠어. 색감이 좀만 더 강해야 할 거 같아. 블러가 먹히는 연출은 멋있는데 생각보다 잘
> 안 느껴지거든."

이 한 문장 안에 서로 다른 네 가지 조정이 섞여 있었다:

1. **색상(hue)**: 보라/자주(violet/magenta) → 파스텔 블루로 팔레트 자체를 교체.
2. **속도(motion)**: 드리프트 벡터 크기를 약 3배로.
3. **채도/강도(saturation)**: `smoothstep` 색상 밴드의 폭을 넓혀(`smoothstep(0.3, 0.7, n)` →
   `smoothstep(0.22, 0.58, n)` 등) 화면에서 밝은 색이 차지하는 면적 자체를 늘렸다 — "색이
   더 강해 보인다"는 인상은 색 그 자체보다 "얼마나 넓게 칠해지는가"에서도 온다는 걸 확인한
   지점이다.
4. **대비(contrast)**: 이건 색 문제가 아니라 **홈 화면과 블러가 걸리는 화면 사이의 밝기 차이가
   너무 작았던 것**이 원인이었다. `u_glow` 값을 홈 0.6/그 외 0.42(차이 0.18)에서 0.75/0.28
   (차이 0.47)로 벌리고, `backdrop-filter: blur()` 값도 60px→95px로 키우자 "블러가 확 걸린다"는
   느낌이 비로소 뚜렷해졌다.

## 질문

- **Q. 옥타브가 몇 개면 적당한가?**
  A. 정해진 답은 없고 "얼마나 자세히 보이는 배경인가"에 달려 있다. 이 프로젝트처럼 콘텐츠
  뒤에 흐릿하게 깔리는 배경은 2개로도 충분했고, 셰이더 자체가 화면의 주인공이라면(예: 실제
  성운 사실적 렌더링) 5개 이상도 흔하다. 옥타브를 하나씩 늘려보면서 "더 자세해 보이는가"와
  "프레임이 떨어지는가"를 눈으로 확인하며 정하는 게 현실적이다.

- **Q. 왜 루프를 쓰나, 언롤링하면 더 빠르지 않나?**
  A. 실행 성능은 거의 같다 — GLSL 컴파일러는 반복 횟수가 상수인 `for` 루프를 대부분 자동으로
  언롤링(unroll)한다. 차이는 성능이 아니라 **코드를 읽고 고치기 쉬운가**다. 옥타브를 3개로
  늘리고 싶을 때 루프면 숫자 하나만 바꾸면 되지만, 언롤링된 코드는 블록을 통째로 복사해야 한다.

- **Q. 별 위치를 결정하는 hash와 색을 결정하는 hash가 왜 따로 있나?**
  A. 같은 시드를 재사용하면 "존재 여부"와 "흔들림 방향/거리"가 서로 상관관계를 갖게 되어,
  우연히도 특정 존재 패턴과 특정 흔들림 패턴이 겹쳐서 규칙적으로 보이는 경우가 생길 수 있다.
  `gi + 0.17`, `gi + 5.31`, `gi + 11.7`처럼 오프셋을 다르게 준 것은 이런 상관관계를 끊기
  위한 값싼 방법이다.

## 예시 코드

실제 `RottenNoble-Project`의 배경 프래그먼트 셰이더에서 별을 그리는 핵심 부분(`frontend/src/
components/SiteBackground/SiteBackground.jsx`):

```glsl
// 셀당 1점 보로노이(Worley) 스타일 샘플링 — 격자 정중앙 대신
// 셀 안에서 랜덤하게 흔든 점에 별을 찍는다.
vec2 starGrid = p * 220.0;
vec2 gi = floor(starGrid);
vec2 gf = fract(starGrid) - 0.5;
vec2 jitter = vec2(hash(gi + 0.17), hash(gi + 5.31)) - 0.5;
float starHash = hash(gi + 11.7);
float starMask = step(0.9965, starHash);
float starDist = length(gf - jitter * 0.8);
float twinkle = 0.6 + 0.4 * sin(u_time * 2.0 + starHash * 40.0);
float star = starMask * (1.0 - smoothstep(0.0, 0.5, starDist)) * twinkle;
```

`step(0.9965, starHash)`가 "이 칸에 별이 있을 확률"을 조절하는 손잡이다 — 임계값을 낮추면
별이 더 많아지고, 높이면 더 드물어진다.

## 실무

웹/게임을 가리지 않고, "배경처럼 화면의 상당 부분을 차지하지만 디테일이 크게 중요하지 않은"
영역에서는 텍스처보다 절차적 셰이더가 실무에서도 흔히 쓰인다 — 에셋 용량이 0이고, 어떤 화면
비율/해상도에도 자연스럽게 맞으며, 시간 유니폼 하나로 애니메이션이 거의 공짜로 따라오기
때문이다. Shadertoy 같은 커뮤니티에 이런 기법의 예시가 아주 많지만, 그곳 셰이더 대부분은
기본 라이선스가 CC BY-NC-SA(비영리·동일조건변경허락·저작자표시)라 코드를 그대로 가져다 쓰면
라이선스 조건이 따라붙는다 — 기법 자체(알고리즘)를 참고하는 것과 특정 셰이더의 코드를 복사하는
것은 구분해야 한다. 최근 동향으로는 WebGPU가 WebGL을 점차 대체해가면서 컴퓨트 셰이더 기반의
더 복잡한 절차적 효과(파티클, 유체 시뮬레이션)가 브라우저에서도 실용적인 성능으로 가능해지는
추세다.
