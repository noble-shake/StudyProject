## 정의

블룸(Bloom)은 화면에서 유난히 밝은 영역(하이라이트)의 빛이 주변으로 은은하게 번져 보이는 효과를
흉내 낸다. 원리는 비교적 단순하다 — 밝기 임계값을 넘는 픽셀만 추출한 뒤, 그 버퍼를 **다운
샘플(축소)했다가 다시 업샘플(확대)하면서 블러**를 여러 단계 적용하고, 마지막에 원본 컬러 버퍼에
합성한다.

## 요약

블룸 자체의 블러 알고리즘은 가볍지만, "다운/업샘플을 반복하며 매 단계 렌더 타겟을 전환한다"는
구조 때문에 GPU와 시스템 메모리 사이의 데이터 전송(대역폭)이 커진다 — 발표자는 이 렌더 타겟
전환 횟수 자체를 줄이는 "미니맥스 블룸" 기법으로 GPU 타임 34%, 메모리 대역폭 27% 개선을
실측했다.

## 상세

### 왜 블룸 최적화가 유독 까다로운가

URP는 블룸에 이미 여러 최적화 옵션(다운샘플 단계 수, 해상도 등)을 제공하지만, 이 옵션들을
건드리면 비주얼이 눈에 띄게 훼손되는 경우가 많다. 특히 아트팀이 이미 특정 블룸 세팅으로 비주얼을
확정해둔 프로젝트에서는, 옵션값을 낮춰서 최적화하는 방법 자체를 쓰기 어렵다 — "품질을 그대로
유지한 채 내부 구현만 싸게 만드는" 접근이 필요해지는 이유다.

### 진짜 병목은 어디인가 — 렌더 타겟 전환 비용

블룸의 다운/업샘플 과정에서는 매 단계마다 해상도가 다른 새 렌더 타겟으로 전환된다. 이 전환이
일어날 때마다, 이전 렌더 타겟의 내용을 시스템 메모리에 저장했다가 다음 단계에서 다시 불러오는
비용이 발생한다 — 이게 누적되면서 메모리 대역폭이 폭증한다는 게 발표자가 짚은 핵심 원인이다.
블러 알고리즘(가우시안 블러) 자체의 연산량이 문제가 아니라, "렌더 타겟을 몇 번이나 갈아
끼우느냐"가 진짜 비용이었다는 뜻이다.

### 미니맥스 블룸(Min-Max Bloom) — 렌더 타겟을 안 바꾸고 영역만 나눈다

발표자가 선택한 최적화는 이렇다: 여러 해상도의 작은 렌더 타겟을 오가는 대신, **하나의 큰 렌더
타겟**을 준비해두고, 그 안을 여러 구역(다운샘플 단계별 영역)으로 나눠 블러 알고리즘 결과를 각
구역에 그린다. CPU에서 미리 계산해둔 사각형(rect) 정보를 커맨드 버퍼의 뷰포트(Set Viewport)
API로 지정해서, 렌더 패스 자체는 그대로 유지하면서 그리는 영역만 이동시키는 방식이다. 이렇게
하면 기존에 다운샘플 단계 수만큼(발표 사례 기준 16회) 필요했던 렌더 타겟 전환이, 처음 한 번만
전환하고 이후엔 전환 없이 9회까지 줄어든다. 블러 알고리즘 자체는 URP 내장 가우시안 블러를 거의
그대로 재사용했다 — 바뀐 건 "그 결과를 어디에 쓰느냐"는 렌더 타겟 관리 방식뿐이다.

### 마지막 합성 — 영역별로 다시 샘플링

블러 결과가 하나의 큰 렌더 타겟 안에 구역별로 나뉘어 저장돼 있으므로, 최종 합성 단계에서는 이
구역들을 영역별로 샘플링해서 합친다. 이 결과물은 기존 우버 포스트 셰이더가 이미 커스텀돼
있다면(예: [톤 매핑](./Tone-Mapping.md) 커스텀과 같은 맥락), 기존 블룸 샘플링 코드 부분만
바꿔주면 비교적 쉽게 적용할 수 있다고 발표자는 설명한다.

### 시도했지만 폐기한 최적화 — 인스턴싱

렌더 타겟이 없어졌으니 이 그리기 호출들을 인스턴스 드로우로 합칠 수 있지 않을까 시도했지만,
결과는 오히려 손해였다. CPU에서 지정하던 뷰포트 사각형을 셰이더 내부에서 계산하도록 바꿔야
했고, 블러 샘플링 시 몇 번을 샘플링할지도 (인스턴스마다 다를 수 없으니) 매직 넘버로 고정할
수밖에 없었다 — 결과적으로 드로우콜은 줄었지만 셰이더 복잡도(ALU 연산량)가 크게 늘어 GPU
타임이 오히려 12% 증가했다. 신기하게도 메모리 대역폭 지표만은 오히려 더 개선됐다고 한다 —
"드로우콜을 줄이는 것"과 "GPU 연산 비용을 줄이는 것"이 항상 같은 방향이 아니라는 걸 보여주는
사례다.

## 비교표

| 방식 | 렌더 타겟 전환 횟수(발표 사례) | 셰이더 복잡도 | 실측 결과 |
|---|---|---|---|
| 기존 URP 가우시안 블룸(다중 RT) | 16회 | 낮음 | 기준값 |
| 미니맥스 블룸(단일 RT, 구역 분할) | 9회 | 기존과 동일 | GPU 타임 34%↓, 메모리 대역폭 27%↓ |
| 미니맥스 블룸 + 인스턴싱 시도 | 9회(변화 없음) | 높음(뷰포트 계산이 셰이더로 이동) | GPU 타임 12%↑(폐기됨), 메모리 대역폭은 추가 개선 |

## 질문

- **Q. 렌더 타겟 전환이 왜 그렇게 비싼가?**
  A. 모바일 GPU(타일 기반 렌더러)는 타일 메모리라는 매우 빠른 온칩 메모리에서 렌더링을 진행하다가,
  렌더 타겟이 바뀌는 시점에 그 결과를 시스템 메모리(더 느리고 전력 소모가 큰 외부 메모리)로 내려쓰고,
  다음 렌더 타겟을 다시 시스템 메모리에서 읽어와야 한다. 이 오가는 과정 자체가 대역폭을 먹는다 —
  타겟을 적게 바꿀수록 이 왕복이 줄어든다.

- **Q. 왜 인스턴싱이 오히려 손해였나?**
  A. 드로우콜 수를 줄이는 최적화는 "CPU가 드로우콜을 준비하는 오버헤드"를 줄이는 데 효과적이다.
  하지만 이 사례는 원래도 CPU 병목이 아니라 GPU 대역폭 병목이었기 때문에, 드로우콜을 줄이는
  대가로 셰이더 연산이 늘어난 게 오히려 GPU 시간을 늘리는 역효과를 냈다 — 최적화 기법을 고를
  땐 먼저 "지금 병목이 CPU인지 GPU인지, GPU라면 연산인지 대역폭인지"를 프로파일링으로 확인해야
  하는 이유다.

## 예시 코드

```csharp
// 개념을 보여주는 최소 예시 — CPU에서 계산한 rect를 커맨드 버퍼 뷰포트로 지정
// (발표에서 언급된 실제 렌더패스 코드의 핵심 아이디어만 재구성)
foreach (var mipRect in downsampleMipRects)
{
    cmd.SetViewport(mipRect);           // 같은 렌더 타겟 안에서 그릴 영역만 이동
    Blit(cmd, sourceTexture, blurMaterial);
}
```

## 실무

실무에서 모바일 GPU 최적화는 "얼마나 적게 계산하느냐"만큼 "렌더 타겟과 메모리 대역폭을 얼마나
아끼느냐"가 중요하다 — 특히 타일 기반 GPU가 대부분인 모바일 환경에서는 렌더 패스/렌더 타겟
전환 자체가 숨은 비용인 경우가 많다. Unity의 렌더그래프(Render Graph) 시스템이 등장한 이유
중 하나도 이런 전환·메모리 수명을 프레임워크 차원에서 자동으로 최적화해주기 위함이다 — 이
사례처럼 손으로 직접 렌더 타겟 관리를 재설계하는 접근은, 프레임워크의 자동 최적화만으로는
부족한 특수한 병목을 잡을 때 쓰는 마지막 카드에 가깝다.
