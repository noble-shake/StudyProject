## 출처

수정)에서 실측된 실제 운영 경험을 정리한 주제.

## 정의

HTTPS는 HTTP 통신을 암호화해서, 중간에서 누군가 트래픽을 가로채도 내용을 못 읽게(또는 조작 못
하게) 만드는 프로토콜이다. 이 암호화를 가능하게 하려면 서버가 **인증서**를 가지고 있어야 하는데,
Let's Encrypt는 이 인증서를 무료로, 자동으로 발급해주는 비영리 인증기관(CA)이다. "Mixed
Content(혼합 콘텐츠)"는 HTTPS로 서빙되는 페이지가 내부적으로 HTTP(암호화 안 된) 자원을 불러오려
할 때 브라우저가 이를 차단하는 현상을 가리킨다.

## 요약

RottenNobleProject는 Let's Encrypt로 실제 인증서를 발급받아 HTTPS 서비스를 운영 중인데, 인증서를
붙이는 작업과 "프런트엔드가 요청을 보내는 API 주소를 HTTPS로 바꾸는 작업"이 서로 다른 시점에
따로 처리되는 바람에, 잠깐이지만 사이트 전체의 API 호출이 mixed content로 막히는 실제 장애를
겪었다 — 인증서를 붙이는 것과 그걸 쓰는 모든 곳을 갱신하는 건 별개의 체크리스트라는 걸 실측으로
확인한 사례다.

## 상세

### Let's Encrypt로 인증서를 받기까지 겪은 것

`MEMO-WEB-06`에 기록된 과정을 보면, 인증서 발급 자체보다 그 전 단계(포트 설정)에서 더 많이
막혔다. Synology NAS는 기본적으로 80/443번 포트를 "기본 서버(default)"가 이미 점유하고 있어서,
`rotten-noble.com`을 위한 새 이름 기반 가상 호스트를 같은 포트로 만들 수 없었다. 그래서 내부적으로
가상 호스트를 8081(HTTP)/8443(HTTPS) 포트로 만들고, 공유기의 포트포워딩에서 외부 80→내부 8081,
외부 443→내부 8443으로 연결해 "밖에서 보기엔 평범한 80/443"으로 보이게 우회했다.

그런데 Let's Encrypt가 인증서를 발급하는 방식(ACME 프로토콜의 HTTP-01 챌린지)은 "외부에서 그
도메인의 80번 포트로 접속해서 특정 파일이 실제로 응답하는지" 확인하는 방식이다. 포트포워딩을
8081로 돌려놓은 상태에서는 이 챌린지 요청이 NAS의 실제 80번(DSM 자체 리스너)이 아니라 엉뚱한
곳으로 가서 계속 발급에 실패했다. 해결책은 발급받는 잠깐 동안만 포트포워딩을 80→80(내부)으로
되돌렸다가, 발급이 끝나면 다시 80→8081로 복귀시키는 것이었다 — 인증서 자체의 기술 문제가 아니라,
"인증 기관이 어떻게 소유권을 확인하는지"와 "이 서버의 포트 구조"가 순간적으로 어긋나서 생긴
문제였다.

### Mixed Content — 인증서를 붙였는데 왜 API가 막혔나

인증서 작업이 끝나고 `https://rotten-noble.com`이 정상적으로 열리게 된 뒤에도, 사이트의 글
목록/방명록이 전부 안 뜨는 문제가 남아있었다. 원인은 `frontend/.env.production`의
`REACT_APP_API_BASE_URL` 값이 여전히 `http://rotten-noble.com/backend`로 남아있었기 때문이다.

```
// MEMO-WEB-07이 기록한 변경
- REACT_APP_API_BASE_URL=http://rotten-noble.com/backend
+ REACT_APP_API_BASE_URL=https://rotten-noble.com/backend
```

브라우저는 `https://`로 열린 페이지 안에서 `http://`로 나가는 요청(fetch, `<script>`,
`<img>` 등)을 기본적으로 차단한다 — 이게 mixed content 차단이다. HTTPS 페이지가 통째로
암호화돼 있어도, 그 안에서 암호화 안 된 요청이 하나라도 섞이면 중간자가 그 요청을 가로채거나
조작할 수 있는 구멍이 생기기 때문에, 브라우저가 아예 원천 차단하는 것이다. 이 프로젝트는 정확히
이 상황에 걸렸다 — 페이지 자체는 HTTPS로 잘 열렸지만, 그 페이지가 내부적으로 요청하는 API
주소가 여전히 HTTP였던 것.

**왜 인증서 작업이 끝났다고 이게 자동으로 안 맞춰졌나.** 인증서는 서버(Apache/Web Station)
설정이고, `REACT_APP_API_BASE_URL`은 프런트엔드 빌드에 박히는 값(빌드 시점에 정적으로
치환됨)이다 — 완전히 다른 계층의, 다른 시점에 처리되는 설정이라 하나를 바꿨다고 다른 하나가
저절로 따라 바뀌지 않는다. `MEMO-WEB-07`은 이걸 "같은 체크리스트 항목으로 묶지 않으면 다음에도
같은 순서로 놓칠 수 있다"고 명시적으로 남겨뒀다.

### 실제로 배포된 값인지 확인한 방법

수정 후 단순히 "값을 바꿨다"에서 끝내지 않고, 실제로 빌드된 번들 파일에서 값이 제대로 박혔는지
`grep`으로 확인했다(`build/static/js/main.*.js`에서 `https://` 문자열 검색). React의 환경변수는
빌드 시점에 코드에 직접 치환되므로, "설정 파일을 고쳤다"와 "배포된 실제 코드에 반영됐다"는 서로
다른 사실이고, 재배포를 빠뜨리면 설정만 고치고 실제로는 옛날 빌드가 계속 서빙될 수 있다.

## 질문

- **Q. Let's Encrypt 인증서는 왜 자동 갱신을 신경 써야 하나?**
  A. Let's Encrypt 인증서의 유효기간은 90일로 짧다(전통적인 상용 인증서의 1년보다 훨씬 짧음) —
  대신 완전 자동 갱신을 전제로 설계됐다. Synology Web Station은 보통 이 갱신을 자동으로
  처리해주지만, 이 프로젝트의 포트 우회 구조(8081/8443 + 포트포워딩)처럼 비표준적인 설정이
  섞여 있으면 자동 갱신 시점에도 처음 발급 때와 같은 문제(ACME 챌린지가 엉뚱한 포트로 감)가
  재발할 가능성이 있다 — 실제로 재발했는지는 아직 확인된 바 없지만, 잠재적 위험 지점으로
  기억해둘 만하다.

- **Q. mixed content 차단은 왜 콘솔 경고가 아니라 완전 차단인가?**
  A. 브라우저 벤더들이 점점 더 엄격하게 정책을 강화해온 결과다. 예전에는 경고만 뜨고 요청이
  나가는 경우도 있었지만, 최신 브라우저는 활성(active) 콘텐츠(스크립트, fetch/XHR 등)에 대해서는
  기본적으로 완전 차단한다 — 이미지 같은 수동적(passive) 콘텐츠는 상대적으로 관대하게 다뤄지는
  경우가 있지만, API 호출은 활성 콘텐츠로 분류돼 예외 없이 막힌다.

## 실무

실무에서도 "인증서는 붙였는데 애플리케이션 설정(API 주소, CDN 주소, 웹훅 URL 등)은 여전히
`http://`로 남아있어서 장애가 난다"는 패턴은 흔하게 반복되는 실수다 — 그래서 많은 팀이 배포
체크리스트에 "모든 하드코딩된 URL을 grep으로 검색"하는 단계를 명시적으로 넣는다. Let's Encrypt는
현재 실무에서 TLS 인증서 발급의 사실상 표준이 됐고(Certbot 같은 자동화 도구와 함께), 유료
인증서를 새로 발급받는 경우는 EV(확장 검증) 인증서처럼 특별한 신뢰 표시가 필요한 경우 정도로
줄었다.
